\chapter{处理器架构与微体系结构}
\label{chap:micro-architecture}

处理器架构是软件与硬件之间的长期契约。编译器、操作系统和固件依赖寄存器、指令、异常、特权级和内存模型；具体处理器则用流水线、缓存、预测器、互连和电源状态实现这些语义。只会查指令编码不足以解释实时长尾、DMA 数据陈旧、异常现场或多核争用，只看某个内核的跑分也不足以证明产品行为。

本章先建立跨架构的分析框架，再分别进入 Armv8-A、Arm Cortex-M 与 RISC-V。各节以架构规范和处理器手册为边界\cite{armpg,armv8m-architecture,riscvspec,riscvpri}；芯片集成、可选扩展和勘误仍必须以目标料号为准。

\section{分清 ISA、微体系结构与平台}

工程讨论中经常把“架构”“内核”和“芯片”混为一谈。至少应区分三层：
\begin{description}
  \item[指令集与体系架构] 定义软件可见状态，例如指令语义、寄存器、异常、特权级、地址转换、内存顺序和原子操作。兼容实现应维持这些语义，但不保证相同周期数。
  \item[微体系结构] 定义如何实现架构，例如流水线深度、发射宽度、顺序或乱序执行、分支预测、缓存与 TLB 容量、预取器和一致性接口。这一层直接影响吞吐、长尾和功耗。
  \item[平台与 SoC] 定义复位、启动地址、中断控制器、定时器、DMA、IOMMU、外设 MMIO、电源域和调试连接。即使使用同一处理器核，不同 SoC 的启动与缓存一致性契约也可能完全不同。
\end{description}

同一 ISA 上的二进制可能可以运行，却具有不同的性能与实时边界；同一处理器核集成到不同芯片后，也可能因互连、DDR、缓存一致性和电源控制产生不同的软件要求。因此兼容声明至少应说明 ISA 版本与扩展、ABI、特权架构、平台规范、内核修订号和 SoC 料号。

\section{从工作负载导出处理器要求}

处理器选型应从目标事务而不是宣传指标开始。代表性工作负载至少描述：
\begin{itemize}
  \item 单次响应截止期、允许抖动和超时后的产品策略；
  \item 持续吞吐、突发长度、并发任务数和数据搬运比例；
  \item 指令、数据、模型与页表工作集，以及访问局部性；
  \item 整数、浮点、SIMD、DSP、密码和自定义加速需求；
  \item 中断频率、DMA 通道、共享外设和跨核通信；
  \item 功耗、热稳态、唤醒延迟、供电能力和电池寿命；
  \item 特权隔离、安全启动、调试生命周期和故障恢复要求。
\end{itemize}

CoreMark、Dhrystone 或单个算子只能回答受限问题。选型报告应固定编译器、优化、链接、内存放置、频率、温度和后台负载，并同时记录吞吐、分位延迟、功耗、温升和降频行为。若工作集全部驻留缓存，得到的结果不能代表 DDR 压力下的产品路径。

\section{指令延迟、吞吐与流水线}

最简执行时间模型为：
\begin{equation}
  T_{\mathrm{exec}} = \frac{N_{\mathrm{inst}}\cdot CPI}{f_{\mathrm{clk}}}
\end{equation}
其中 $N_{\mathrm{inst}}$ 受算法、ISA 和编译器影响，平均每指令周期数 $CPI$ 则由微体系结构和运行时事件共同决定。更高频率不一定带来同比加速，因为电压、等待状态、缓存未命中、热降频和共享资源可能同时变化。

流水线把取指、译码、执行、访存和提交重叠。数据相关、结构冲突、分支误预测、指令缓存未命中和序列化操作都会形成气泡。乱序执行可以隐藏部分延迟，但不能消除真实依赖，也不能无限覆盖 DDR、MMIO 或页表遍历的长延迟。

手册中的“延迟”和“吞吐”必须区分：某指令的结果可能若干周期后才可被依赖指令使用，但执行单元可以每周期接收一个新的独立操作。测量时还要防止编译器删除、合并或搬移目标代码，并检查反汇编确认实际指令序列。

对实时任务，仅有平均 CPI 没有证明力。应在最坏中断嵌套、缓存冷启动、总线竞争、页表活动和热限制下测量尾部延迟，并把无法建模的干扰纳入资源隔离或超时策略。第~\ref{chap:performance-capacity-engineering}~章进一步讨论负载模型、分位数与容量验收。

\section{存储层次通常决定系统上限}

寄存器、缓存、TCM/SRAM、DDR 和非易失存储在容量、延迟、带宽、功耗与持久性之间交换。处理器还可能具有独立的指令/数据缓存、多级共享缓存、写缓冲、预取器和 TLB。一次 load 的成本因此不是常数，而取决于地址翻译、缓存命中、内存属性、互连仲裁和其他主设备。

缓存提高平均性能，也引入冷启动、冲突、替换和一致性成本。两个核修改同一 cache line 中互不相关的变量会产生 false sharing；实时任务与高带宽任务共享 LLC 或 DDR 时，独立 CPU affinity 也不能消除干扰。关键缓冲应按工作集、cache line、NUMA/内存控制器和 DMA 路径共同布局。

MMIO 不能按普通 RAM 推理。设备内存可能禁止推测、合并或乱序，但精确定义取决于架构内存类型和映射属性。posted write 还可能在 CPU 看来已经完成时仍停留在互连或设备队列中；启动 DMA、复位外设或切换电源域前，需要使用平台规定的 accessor、屏障或读回机制。

DMA 是否与 CPU 缓存一致是 SoC 属性，不由 ISA 名称决定。非一致平台必须定义缓冲所有权、cache maintenance 的方向与范围、完成中断后的可见性和复位恢复。共享内存与跨核所有权见第~\ref{chap:heterogeneous-multicore}~章，语言原子、屏障与 DMA 边界见第~\ref{chap:realtime-language-memory-model}~章。

\section{异常、特权与隔离}

异常模型决定复位、系统调用、中断、页错误和故障如何转移控制。架构通常定义保存的最小状态和返回语义，微体系结构与平台则决定入口流水线、向量获取、中断控制器仲裁和总线等待。可用下式拆分中断响应：
\begin{equation}
  L_{\mathrm{irq}} = L_{\mathrm{mask}} + L_{\mathrm{finish}} + L_{\mathrm{entry}} + L_{\mathrm{dispatch}}
\end{equation}
$L_{\mathrm{mask}}$ 是软件或更高优先级活动造成的屏蔽时间，$L_{\mathrm{finish}}$ 表示当前不可中断操作和总线事务，后两项分别对应架构入口与软件分发。缓存/TLB 未命中、栈存储、共享互连和安全状态切换都可能放大这些分量。

特权级、MPU/MMU、虚拟化和 IOMMU 解决不同对象的隔离。CPU 页表不能自动约束 DMA，MPU 区域也不能替代总线防火墙；Hypervisor 能隔离客户机 CPU 和内存访问，却仍需设备复位、直通和中断重映射支持。系统隔离方法见第~\ref{chap:virtualization-isolation}~章。

故障处理必须保存足够的架构状态，同时避免诊断路径再次访问损坏资源。至少需要异常原因、PC/SP、特权级、地址转换或总线状态、处理器/SoC 修订号和固件 build ID。微体系结构错误或异步总线错误可能在真正触发点之后才被报告，不能把异常 PC 直接当成根因。

\section{并发、原子与内存顺序}

“一条指令完成”不等于“其他观察者已经看到”。编译器重排、CPU 乱序、缓存和互连缓冲都会改变观察顺序。架构内存模型定义允许的结果；语言内存模型定义 C/C++/Rust 程序何时具有数据竞争以及 acquire/release 等语义；操作系统 accessor 再把这些语义映射到具体平台。

原子读改写可能由专用指令、load-linked/store-conditional、exclusive monitor 或锁实现。是否 lock-free、竞争下是否前进、最坏重试次数和公平性均取决于类型、对齐、实现与干扰。中断、另一核、DMA 或调试器是否会破坏监视状态，也必须查目标手册。

屏障不是越多越正确。编译器屏障只约束编译器；内存屏障约束指定观察者和访问类型；指令同步屏障刷新取指上下文；设备完成还可能需要状态读回。错误屏障既可能遗漏设备边界，也可能把高频路径串行化。

\section{功耗、温度与运行模式}

动态功耗通常随开关活动、电容、电压平方和频率变化，漏电则受工艺、电压与温度影响。DVFS、时钟门控、电源门控、缓存保持和深睡眠不是独立开关，而是带进入条件、状态保存、唤醒源和失败恢复的状态机。

性能验收必须覆盖热稳态。短时基准可能一直处于峰值频率，而产品长时间运行后因结温、PMIC 电流或平台功耗预算降频。实时系统还要验证最慢合法频点和唤醒后的缓存冷启动，不能只在实验室冷机状态证明截止期。

低功耗策略应比较每次事务能量和空闲窗口，而不是只看某个状态的静态电流。更深状态降低驻留功耗，却增加保存、恢复、时钟稳定和外设重建成本；完整方法见第~\ref{chap:low-power-system}~章。

\section{资料层级与验证闭环}

面对一个新平台，应按层级建立资料清单：
\begin{enumerate}
  \item 架构规范：指令、异常、内存模型和特权语义；
  \item 处理器 TRM：缓存、预测器、PMU、调试和实现选项；
  \item SoC 手册：地址图、中断、DMA、互连、电源、复位和启动；
  \item 板级资料：时钟、电源、存储器、strap、连接器和调试链路；
  \item 勘误与安全公告：受影响修订、触发条件、workaround 和移除条件；
  \item 工具链与 ABI：代码模型、原子库、异常展开、链接和启动约定。
\end{enumerate}

文档结论应通过最小实验闭环验证：固定硬件与软件版本，构造单一假设，检查反汇编和映射文件，在目标板采集 PMU/trace/逻辑分析证据，再用边界负载和故障注入复验。模拟器适合验证架构功能和启动流程，但通常不能证明真实缓存、互连、DDR 与功耗时序。

项目应维护一份机器可读的平台 manifest，记录 ISA 与扩展、处理器修订号、缓存 line 大小、一致性域、计时器频率、可用 PMU 事件、启动接口和已应用勘误。这样性能结果、崩溃记录和发布镜像才能关联到同一硬件事实。

\section{架构评审清单}

\begin{itemize}
  \item ISA、ABI、特权架构、处理器修订号和 SoC 料号是否分别记录？
  \item 代表性工作负载是否覆盖缓存冷启动、DDR 竞争、热稳态和最低合法频点？
  \item 中断、异常、页错误和异步总线错误的证据是否可离线解析？
  \item MMIO、DMA、共享内存和语言原子是否使用各自正确的顺序与所有权契约？
  \item MPU/MMU、IOMMU、总线防火墙和调试权限是否覆盖所有主设备与生命周期？
  \item 模拟器、基准和目标板测量各自证明什么，不能证明什么，是否写入报告？
  \item 勘误 workaround 是否绑定修订号、测试证据与未来移除条件？
\end{itemize}
