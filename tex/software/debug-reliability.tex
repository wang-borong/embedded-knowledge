\chapter{调试与可靠性工程}
\label{chap:debug-reliability}

嵌入式故障经常跨越电源、时钟、信号、处理器、内核和应用边界。
有效调试依赖可观测性、可复现条件和逐层缩小范围，而不是反复修改代码等待现象消失。
可靠性工程则要求在交付前主动构造极端负载、资源耗尽、掉电和器件异常，证明系统能够检测、隔离并恢复故障。

\section{分层故障模型}

建议按以下层次建立假设：
\begin{enumerate}
  \item \textbf{供电与复位}：电压、纹波、时序、欠压、复位脉宽和启动模式；
  \item \textbf{时钟与信号}：晶振、PLL、总线时序、电平、终端和信号完整性；
  \item \textbf{处理器执行}：取指地址、异常向量、栈、MMU、缓存和内存；
  \item \textbf{系统软件}：Bootloader、内核、驱动、文件系统和服务依赖；
  \item \textbf{应用与数据}：协议状态、资源泄漏、并发、配置和持久化一致性。
\end{enumerate}

每次实验应只改变一个关键变量，并保留镜像摘要、配置、硬件版本、环境条件和完整日志。

\section{故障签名、假设与证据保全}

故障描述应从“偶尔死机”收敛为稳定签名，至少包括触发条件、首个异常观测、受影响执行域、复位原因、恢复结果和出现概率。最后一条日志通常只是系统仍能记录的最后位置，不自动等于根因；真正的起点可能是更早的电源跌落、内存破坏或队列积压。

调试开始前先保护证据。重启、重刷、清空数据、拔掉电源或更换工装都可能永久覆盖崩溃区、文件系统状态、复位寄存器和时序关系。产品应定义最小保全顺序，例如先读取复位原因与 retention SRAM，再导出崩溃记录和版本 manifest，最后才执行恢复动作。

每轮实验建议记录：
\begin{itemize}
  \item 当前事实、待验证假设和能够推翻该假设的观测；
  \item 唯一改变的变量，以及其余受控变量；
  \item 原始证据、工具设置、时间基准和测量不确定度；
  \item 结果是否支持、反驳或无法判断假设；
  \item 下一步实验为何能进一步缩小范围。
\end{itemize}

负面证据也需要确认观测链有效。“没有 UART 输出”可能表示代码未执行，也可能是串口时钟、pinmux、采集线或日志缓冲失效。可以先产生已知测试脉冲、读回状态寄存器或使用第二观测通道验证仪器确实能够看到目标事件。

\section{二分定位与对照实验}

高效定位的核心是选择能够最大幅度分割假设空间的实验。最小 initramfs 能启动、正式 rootfs 不能启动，会把问题从 CPU/DRAM/内核主路径收敛到存储、挂载和用户空间；同一镜像在参考板通过、目标板失败，则优先比较硬件 revision、器件批次、供电、时钟和校准。

替换法每次只交换一个元素：DUT、镜像、存储介质、电源、线缆、外设、工装通道或网络环境。所谓 known-good 资产也要有版本和自检；若参考板与问题板共享同一错误电源或同一批次器件，对照会给出虚假结论。

软件回归可以按提交或发布产物二分，但必须保持工具链、配置、Device Tree、固件和数据 schema 兼容。只切换应用二进制却沿用不兼容内核，可能产生一个历史上从未发布过的组合。每个二分点应保存完整 manifest 和自动判定器，避免人工观察随轮次漂移。

\section{硬件观测工具}

\subsection{万用表与电子负载}

万用表适合确认稳态电压、电阻、短路和连续性，不能替代示波器观察瞬态跌落和高频纹波。
电子负载可验证电源限流、负载瞬态和热稳定性。测量低电阻或大电流路径时，应考虑表笔和走线压降，并优先使用四线法或专用电流采样。

\subsection{示波器}

示波器测量的可信度取决于探头带宽、接地回路、输入阻抗、采样率和触发条件。
观察电源纹波时应使用短接地弹簧和适当带宽限制；观察高速边沿时，长鳄鱼夹接地线本身可能产生足以误导判断的振铃。

常见触发对象包括欠压、异常复位、总线错误、过长中断脉冲和启动时序。应同时观测因果相关信号，例如电源轨、复位、时钟和故障 GPIO。

\subsection{逻辑分析仪与协议分析}

逻辑分析仪适合捕获数字时序和长时间协议事件，但其阈值模型不能反映模拟电平质量。
协议解码结果必须结合原始波形、采样率和触发位置审查，避免把边沿失真或电气冲突误判为纯协议错误。

\section{跨仪器触发与测量边界}

电源、复位、总线、处理器 trace 和应用事件往往由不同仪器采集。关键实验应使用公共触发信号、可测 GPIO 脉冲或共享参考时钟，把波形与软件事件关联；仅按屏幕时间大致对齐，无法区分因果顺序在微秒级的异常。

触发点要尽量靠近被验证边界。例如分析“写寄存器后外设未动作”，可以同时采集 CPU trace 中的 MMIO 提交、总线片选、设备 IRQ 和电源轨。若只看到应用日志“命令已发送”，仍无法证明写访问离开了 CPU 或到达外设。

采样系统也会产生假象。数字分析仪采样率不足会遗漏窄脉冲，示波器存储深度不足会在长窗口降低有效采样率，AC coupling 会隐藏直流偏移，探头负载可能改变晶振和高阻节点。报告应保存探头、带宽限制、量程、采样率、记录长度、触发条件和校准状态。

插桩会扰动被测系统：串口日志增加锁与 I/O，GPIO 翻转改变时序，断点会让外设继续运行而 CPU 停止，trace 带宽不足会丢包。关键结论应使用至少两种侵入程度不同的方法交叉验证，并说明停核调试对多核、DMA、看门狗和执行器的影响。

\section{从复位到用户空间的调试路径}

\subsection{无输出系统}

当系统没有串口输出时，推荐依次确认：
\begin{enumerate}
  \item 电源轨和复位是否满足数据手册要求；
  \item 启动 strap、存储器和 Boot ROM 下载模式是否正确；
  \item JTAG/SWD 能否连接，处理器停在何处；
  \item 异常向量、栈指针和程序计数器是否位于有效区域；
  \item 串口的时钟、引脚复用、电平和波特率是否匹配；
  \item DRAM 初始化前后执行路径是否发生变化。
\end{enumerate}

不要在尚未证明 DRAM 稳定时依赖复杂日志和动态内存。早期启动应保留最小串口、状态 GPIO 或片上 SRAM 日志路径。

启动链可以为每个不可逆阶段写入小型里程碑，例如 Boot ROM 交接、PLL 完成、DRAM 训练、镜像验证、MMU 开启、内核入口和 PID 1 ready。里程碑应包含 boot ID、阶段 ID、错误码和校验，并写入 retention SRAM、always-on 寄存器或受控持久区；下次启动先读取旧记录，再开始新的序列。

里程碑不能无界写 Flash。高频启动或 brownout 循环会快速消耗固定扇区，应使用有界环、写入限速、介质友好元数据或只在失败路径提交。复位原因寄存器也可能在读取或后续复位时清除，Bootloader 应尽早快照并向后级传递。

安全启动启用后，调试权限本身具有生命周期。量产锁定设备可能拒绝 JTAG/SWD，维修解锁可能触发擦除或改变密钥状态。调试计划应预留受控签名镜像、认证调试或专用工程样机，不能在现场故障发生后才发现唯一证据通道已永久关闭。

\subsection{Linux 启动问题}

Linux 启动调试应保留 Bootloader 环境、内核命令行、设备树摘要和从最早 console 开始的日志。
发生挂起时，可通过 early console、initcall 调试、动态调试或临时 tracepoint 确定阶段。
如果最小 initramfs 能启动，而正式根文件系统不能启动，问题通常已收敛到存储、挂载、用户空间依赖或安全策略。

QEMU 可以快速验证内核配置、启动参数和部分驱动逻辑，但模拟器不能证明真实电源、时钟、DMA、一致性和外设时序正确\cite{qemu-system-doc}。

\subsection{QEMU 与 GDB 内核调试}

可重复的内核调试环境至少固定 QEMU machine、CPU 型号、内存容量、内核配置、DTB、rootfs 和命令行。内核应保留 \texttt{CONFIG\_DEBUG\_INFO}，并用未剥离的 \texttt{vmlinux} 提供符号；QEMU 实际加载的压缩镜像与 GDB 使用的符号文件必须来自同一次构建。
GDB 的远程协议、架构支持和命令行为随版本演进，调试脚本应固定版本并参考对应手册\cite{gdb-manual}。

\begin{lstlisting}[language=bash,caption={QEMU 停机等待 GDB 的启动方式（AArch64 示例）}]
qemu-system-aarch64 \
  -machine virt -cpu cortex-a57 -m 1024 -nographic \
  -kernel Image -initrd rootfs.cpio \
  -append 'console=ttyAMA0 earlycon nokaslr' \
  -S -gdb tcp:127.0.0.1:1234
\end{lstlisting}

\begin{lstlisting}[language=bash,caption={GDB 连接内核}]
gdb-multiarch vmlinux
(gdb) target remote 127.0.0.1:1234
(gdb) hbreak start_kernel
(gdb) continue
\end{lstlisting}

关闭 KASLR 便于初始学习和符号定位，不能据此形成发布配置。调试模块时还需要根据目标系统中的实际加载地址执行 \texttt{add-symbol-file}；调试早期页表切换时，应区分链接虚拟地址、加载物理地址和当前 MMU 状态。

QEMU 适合验证启动流程、异常路径、锁与部分虚拟设备驱动。涉及缓存一致性、DMA 时序、中断丢失、PHY、模拟电气和真实闪存故障时，必须回到目标硬件和硬件在环环境复验。

\section{调试构建与发布构建的差异}

调试配置常关闭优化/KASLR、启用额外断言、扩大栈、改变 allocator，并加入 sanitizer 或 trace。这些变化可能修复竞态、改变内存布局或掩盖资源不足。缺陷只有在接近发布的编译器、优化、LTO、链接脚本、内核配置和安全策略上复验后，才能认为边界已被理解。

建议维护机器可比较的配置差异清单，标识每个调试选项对 ABI、时序、内存和安全的影响。若必须用侵入式配置捕获证据，可以先由它定位假设，再逐项移除诊断开关，确认最小插桩仍能观察问题且修复在正式配置生效。

所有地址、调用栈和模块偏移必须关联 build ID。不能因为源码提交相同就假定符号一致：编译器、链接顺序、配置、LTO、签名和后处理都可能改变最终地址。符号服务应按不可变 build ID 查找，而不是按“latest”或人工版本名覆盖。

\section{软件调试与追踪}

\subsection{固件调试}

GDB、JTAG/SWD 和硬件断点适合控制执行与检查寄存器。观察实时系统时要注意停核可能改变外设、看门狗和多核时序。
对于难以复现的故障，应使用环形事件记录、硬件 trace 或在复位后保留的故障区，而不是只依赖交互式单步。

异常处理程序至少应保存异常原因、程序计数器、栈指针、关键寄存器、任务标识和固件版本。
解析工具必须使用与目标镜像完全对应的 ELF 和映射文件。

\subsection{Linux 故障信息}

内核 oops 和 panic 的价值取决于符号、配置和镜像匹配。
产品应归档未剥离的 \texttt{vmlinux}、模块符号、System.map、配置和源码提交。
pstore/ramoops 可以跨重启保存有限的崩溃信息\cite{linux-pstore}；kdump 适用于资源允许且需要完整内存转储的系统\cite{linux-kdump-doc}。

性能与时序问题可使用：
\begin{itemize}
  \item \textbf{ftrace/trace-cmd}：函数、调度、中断和内核事件\cite{linux-ftrace-doc}；
  \item \textbf{perf}：硬件计数器、采样和调用栈；
  \item \textbf{eBPF}：受控地观测内核和用户空间事件；
  \item \textbf{lockdep、KASAN、KCSAN、UBSAN}：锁、内存和并发错误检测；
  \item \textbf{kmemleak 与专用统计}：泄漏和资源生命周期分析。
\end{itemize}

诊断配置会显著改变内存、性能和时序。发现问题后必须在接近发布的配置中复验。

\section{崩溃证据与符号化流水线}

不同故障需要不同证据层级。MCU HardFault 可以保存堆叠寄存器、异常状态寄存器、当前任务和有限栈窗口；Linux 用户进程可以保存 core/minidump、映射表与线程栈；内核 panic 可使用 pstore 或 capture kernel；远端核则需要独立 panic 区和主核导出路径。证据格式应版本化并能部分解析，不能因新增字段让旧工具完全失效。

上传前先生成摘要并记录采集状态。内存不足、存储损坏或复位过快时，诊断包可能只包含部分线程或被截断日志；采集器应明确哪些项成功、失败和丢失，而不是生成一个看似完整的空包。敏感内存、密钥、用户数据和网络凭据需要分级、脱敏与访问审计。

符号化服务至少验证 build ID、架构、模块加载地址和转储格式，再生成函数、文件/行和内联栈。若符号不匹配，应停止并报告需要的确切标识，不能用相近版本“猜”出一个看似合理的调用栈。原始地址和原始转储应与符号化结果一起保存，以便工具升级后重新解析。

崩溃证据还应与前序事件关联：boot ID、transaction ID、最后进展点、资源水位、更新状态和复位原因。单独的调用栈常只能说明在哪里崩溃，无法解释为什么此时到达该状态。

\section{不可复现与并发故障}

难以复现通常表示关键变量尚未被控制，而不是故障不存在。应系统记录 CPU affinity、IRQ 路由、频率、温度、内存压力、网络时延、随机种子、外设批次和启动历史，并通过负载放大或调度扰动提高触发概率。

增加日志后故障消失是典型 Heisenbug。可改用有界二进制事件环、硬件时间戳、采样 trace 或 CoreSight 等低侵入硬件跟踪\cite{linux-coresight-doc}。事件记录应固定 ID、长度和丢包计数；缓冲区溢出时保留故障前窗口还是故障后窗口，需要由场景决定。

对竞态问题，重点寻找“必要顺序”而非完整重放全部线程。记录锁获取/释放、队列 generation、对象生命周期、IRQ/任务切换和关键原子值，建立最小 happens-before 关系。暂停单核可能破坏多核竞态，断点调试只能作为辅助，不能当作竞态不存在的证据。

统计触发概率时必须保持前置条件一致。一次运行包含 1000 次事务，与 1000 次独立冷启动具有不同状态历史；重试前清空数据、换板或复位会改变样本。报告应说明实验单位、暴露次数和基础设施中断，而不只写“跑了三天”。

\section{测试层次}

\subsection{静态检查与单元测试}

编译告警、静态分析、格式检查、设备树 schema、配置检查和链接布局检查应作为提交门禁。
纯算法、协议解析和状态机应尽量从硬件访问中分离，使其能够在主机环境进行快速单元测试和模糊测试。

\subsection{集成测试与硬件在环}

集成测试验证真实驱动、服务和外设之间的契约。硬件在环（Hardware-in-the-Loop, HIL）系统可以控制电源、复位、输入信号、网络和测量设备，并自动收集串口、功耗和测试结果。

HIL 工装必须自身可校准、可版本化，并能区分被测设备故障和测试基础设施故障。
具体的场景契约、故障注入证据、硬件农场和 flaky 治理见第~\ref{chap:test-automation-hil}~章；本章重点保留如何使用这些证据收敛根因。

\subsection{压力与耐久测试}

压力测试应覆盖比标称负载更恶劣但仍在设计边界内的条件：
\begin{itemize}
  \item CPU、内存、存储和网络并发满载；
  \item 高频中断、队列拥塞和连接反复建立；
  \item 文件系统接近满载及日志持续写入；
  \item 长时间挂起恢复、热插拔和服务重启；
  \item 温度、电压和时钟容差边界；
  \item 多日或多周运行中的泄漏、计数器溢出和时间漂移。
\end{itemize}

测试结果应记录最大值和分布，而不仅是平均值。实时延迟和启动时间通常更关心最坏值或高分位数。

\section{故障注入}

故障注入用于验证错误路径，而不是破坏性地随机操作系统。每个注入点应对应一个预期检测机制、超时、告警和恢复结果。

常见场景包括：
\begin{itemize}
  \item I2C/SPI/CAN 超时、CRC 错误和设备无响应；
  \item DMA 未完成、中断丢失或中断风暴；
  \item 内存分配失败、队列满和文件描述符耗尽；
  \item 存储读写失败、坏块增加和文件系统损坏；
  \item 网络断开、DNS 失败、证书过期和服务器返回异常；
  \item 在镜像写入、元数据提交和首次启动期间断电；
  \item 关键任务卡死、进程崩溃和看门狗复位。
\end{itemize}

故障恢复必须具有时间上限。无限重试既可能阻塞系统，也会放大器件故障和网络拥塞。

注入命令发出不等于故障已经发生。每个场景都应证明注入点确实改变了物理或软件状态，随后证明检测机制在规定时间内触发，并最终验证隔离、降级、恢复和持久数据不变量。缺少其中任一段，只能说明测试脚本运行过。

故障强度必须对应真实假设。总线短暂毛刺、设备持续无响应和线路硬短路具有不同能量与恢复语义；内存分配一次失败与长期内存耗尽也应触发不同策略。过度故障注入可能损坏器件或创造现场不可能出现的组合，需要限能、联锁和危害评审。

恢复路径还要验证故障撤销后的行为：锁存告警是否按授权清除，重连是否形成风暴，事务是否重复执行，降级配置是否能恢复，备用通道是否被同步。系统“重新在线”不代表业务状态已经一致。

\section{看门狗与健康管理}

看门狗只能证明负责喂狗的执行路径仍在运行，不能自动证明系统健康。
可靠设计通常由健康管理任务汇总关键任务心跳、调度延迟、资源水位和外设状态，只有所有必要条件满足时才刷新硬件看门狗。

看门狗超时必须大于经过验证的最长正常阻塞时间，同时小于产品允许的故障恢复时间。
复位后应持久化复位原因和有限诊断上下文，并限制反复重启：连续失败达到阈值时进入恢复或安全模式。

\subsection{分层看门狗与 progress 证明}

单个任务喂硬件狗容易形成假健康。更可靠的结构是各关键任务发布带 generation 的 progress token，健康管理器检查采样、控制、通信和存储事务都在各自窗口内前进，再由一个受限路径刷新 SoC 或外部看门狗。心跳只证明任务被调度，progress 才能发现“线程运行但一直处理同一失败事务”。

窗口看门狗可以检测过早刷新，外部 supervisor 能覆盖 SoC 时钟或内部看门狗失效，但二者仍需验证供电、复位脉宽和启动模式。若复位输出也会影响执行器、通信伙伴或存储，必须分析系统级后果，不能只验证 CPU 能重新启动。

调试和升级模式需要明确看门狗策略。永久禁用会让关键恢复机制未被测试，简单延长又可能超过故障反应时间。可以使用签名维护模式、独立安全输出和受控超时，并在退出后验证正式窗口恢复。

启动循环策略应区分一次偶发复位、同一版本连续失败和跨版本失败。达到阈值后应冻结部分证据、停止重复破坏数据，并选择已知良好槽、最小恢复环境或安全停机；“无限自动重启”会把初始根因转化为存储磨损和证据丢失。

\section{可靠性设计}

\subsection{失效安全与降级}

系统应定义故障时的安全状态。例如停止执行器、保持最后安全输出、关闭高功率通道或切换备用传感器。
“继续运行”不是默认正确策略；应根据危害分析决定停机、降级或冗余接管。

\subsection{资源与寿命预算}

可靠性预算包括 RAM/Flash 裕量、CPU 峰值、存储写放大、擦写寿命、日志速率、电源余量和热裕量。
监控指标应与这些预算直接对应，并设置趋势告警，避免只有资源完全耗尽后才暴露问题。

\subsection{任务剖面、故障域与冗余}

可靠性结论必须绑定任务剖面：温度驻留、每日启停、写入量、网络重连、执行器动作和负载占空比。实验室连续满载可以发现热和资源问题，但不能自动代表频繁冷启动、潮湿停放或长时间低功耗唤醒的现场机理。

设计应明确 fault containment region。两个“冗余”通道若共享电源、时钟、总线、软件更新、配置或同批器件，仍可能被共同原因同时击穿。切换备用通道前要验证其数据新鲜度、校准、输出状态和接管时间，不能只检查它是否在线。

降级模式也需要资源和时序预算。关闭非关键服务可能释放 CPU，却可能同时关闭日志、时钟同步或散热控制；保持最后输出可能在短暂传感器故障中安全，却在执行器卡死时增加危害。每个降级状态应有进入条件、允许驻留时间、对外语义和退出验证。

\section{根因、逃逸与 FRACAS 闭环}

根因分析至少区分四类事实：触发事件、潜在缺陷、为何验证未发现、为何现场影响被放大。例如掉电是触发，元数据提交顺序错误是缺陷，HIL 未覆盖该窗口是逃逸原因，反复自动重启覆盖日志则是放大因素。

修复完成不只意味着触发点代码改变，还应增加能防止同类缺陷再次逃逸的测试、静态规则、监控或设计约束。若只能降低出现概率，应记录残余风险、适用条件、观测指标和进一步退出条件。

FRACAS 记录应关联设备/批次、硬件与软件版本、故障签名、原始证据、临时遏制、根因、纠正措施和验证结果。相同签名在不同版本再次出现时，应能查询先前假设与修复，而不是重新从零调查。制造与现场质量闭环可结合第~\ref{chap:product-qualification-quality}~章的方法。

\section{发布验收清单}

\begin{itemize}
  \item 是否能够根据版本号找到对应源码、配置、符号、设备树和镜像摘要？
  \item 故障签名、首个异常观测、假设和每次实验变量是否可追踪？
  \item 重启、重刷或换板前是否按规定保全复位原因、崩溃区和持久状态？
  \item 是否定义并测量了启动时间、实时延迟、资源峰值和功耗上限？
  \item 是否完成关键接口、满载、长稳、低功耗和温度边界测试？
  \item 是否对所有关键错误路径执行过故障注入？
  \item 注入是否证明故障实际发生、被检测并完成有界恢复？
  \item 看门狗、崩溃转储、复位原因和恢复模式是否经过端到端验证？
  \item 调试配置发现的结论是否在完全匹配的发布配置和符号上复验？
  \item 测试失败是否能关联到硬件版本、软件版本、工装和原始日志？
  \item 根因分析是否区分触发、缺陷、逃逸和放大因素，并形成防再发资产？
  \item 发布配置是否消除了未解释告警，并保留必要的生产诊断能力？
\end{itemize}
