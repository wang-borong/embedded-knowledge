\chapter{嵌入式功能安全}
\label{chap:functional-safety}

功能安全关注系统在故障发生时是否仍能避免不可接受的风险。它不是“代码质量更高”的同义词，也不是在开发末期增加看门狗和测试用例；安全活动必须从危害分析、系统架构、硬件诊断到软件验证形成可追溯闭环。

IEC~61508 给出跨行业的功能安全基础框架，汽车、工业机械、铁路和医疗等领域还具有各自派生标准\cite{iec61508,iso26262}。具体项目必须依据适用法规和认证范围执行，本章只讨论通用工程方法。

\section{安全、可靠性与信息安全}

可靠性关注系统持续无故障工作的概率；功能安全关注故障是否导致危害；信息安全关注恶意行为造成的机密性、完整性和可用性风险。三者相互影响但不能互相替代。

一个系统可能经常进入安全停机，因此可靠性不高但安全；也可能长期稳定运行，却在一个罕见传感器故障时输出危险命令。网络攻击同样可能触发安全危害，因此安全分析需要与第~\ref{chap:security-lifecycle}~章的信息安全生命周期交换假设和措施。

\section{危害分析与安全目标}

危害分析从系统功能、运行环境、人员暴露和可控性出发，识别危险事件并确定风险等级。安全目标应描述必须避免的危害状态，例如“检测到位置反馈不可信后，在规定时间内撤销驱动输出”，而不是直接指定某个软件实现。

安全目标进一步分解为功能安全需求和技术安全需求，每条需求都应具有来源、分配对象、验证方法和状态。需求工具不是关键，关键是能够从危害一路追踪到架构、代码、测试和残余风险。

\section{安全状态与故障反应时间}

系统必须定义每类故障的安全状态。安全状态可能是断电、制动、保持受控输出、限速运行或切换冗余通道，并不总是“全部关闭”。

故障容忍时间间隔（Fault Tolerant Time Interval, FTTI）限定从故障发生到危害形成的最大时间。诊断周期、故障确认、通信延迟和执行器响应之和必须小于 FTTI：
\begin{equation}
  T_{detect}+T_{decide}+T_{communicate}+T_{actuate}<T_{FTTI}
\end{equation}

看门狗周期和任务健康检查必须从该预算推导，不能凭经验设置。

\section{安全架构与独立性}

常见机制包括双通道比较、不同原理冗余、锁步核、ECC/Parity、独立看门狗、电压与时钟监控、端到端通信保护和安全岛。冗余只有在共因失效受到控制时才有效；两个相同传感器共享同一电源和线束，不能自动视为独立通道。

安全监控器应比被监控功能简单，并具有独立资源和直接进入安全状态的能力。复杂 Linux 应用可以提出控制请求，但最终输出约束可由 MCU、安全岛或硬件逻辑执行。

\section{硬件诊断覆盖}

硬件安全分析通常区分随机硬件故障与系统性设计缺陷。常见诊断包括：
\begin{itemize}
  \item RAM/Flash ECC、启动自检和周期性内存测试；
  \item CPU 寄存器、控制流和锁步比较；
  \item 时钟、欠压、过压和温度监控；
  \item ADC 合理性、传感器范围和变化率检查；
  \item 输出回读、电流检测和断线/短路诊断；
  \item 通信 CRC、序号、超时、发送方/接收方 ID 与数据新鲜度。
\end{itemize}

诊断覆盖率必须针对具体失效模式评估。一个 CRC 可以发现传输位翻转，却不能发现发送方软件持续生成语义错误的合法报文。

\section{安全软件架构}

安全软件应限制动态行为和隐式共享状态。推荐使用静态资源、明确任务周期、受控 IPC、超时、范围检查和单向依赖。高等级模块与普通功能共存时，应证明空间、时间和通信干扰受到隔离。

\begin{lstlisting}[language=C,caption={带数据新鲜度和合理性检查的安全输入}]
bool accept_sample(const struct sample *s, uint32_t now)
{
    if (!crc_valid(s) || s->source_id != EXPECTED_SOURCE)
        return false;
    if (sequence_distance(last_seq, s->sequence) != 1U)
        return false;
    if ((now - s->timestamp) > MAX_SAMPLE_AGE)
        return false;
    if (!in_range(s->value) || !rate_is_plausible(last_value, s->value))
        return false;
    last_seq = s->sequence;
    last_value = s->value;
    return true;
}
\end{lstlisting}

错误处理本身也必须可分析。断言在开发阶段适合暴露违约，但产品中应根据安全需求进入复位、降级或安全状态，并保存有限诊断信息。

\section{开发过程与工具置信度}

功能安全关注系统性失效，因此需要需求评审、架构评审、编码规范、静态分析、独立验证和变更影响分析。编译器、代码生成器、测试工具和校准工具若可能引入或漏检安全错误，需要评估工具置信度并采取验证、限定使用或工具认证措施。

“通过 MISRA 检查”不等于满足安全目标。编码规则只能降低部分缺陷概率，不能替代需求正确性、并发分析、硬件故障分析和目标环境测试。

\section{验证、确认与故障注入}

单元测试验证模块逻辑，集成测试验证接口，系统确认验证安全目标是否在真实使用环境中满足。故障注入应覆盖传感器卡死、偏移、通信丢失、内存错误、任务超时、电源异常和执行器故障，并检查检测时间与最终安全状态。

安全测试需要需求覆盖和结构覆盖，但覆盖率只是证据之一。无法通过测试覆盖的防御代码，应通过分析、故障注入或受控触发证明其行为。

\section{安全案例与变更管理}

安全案例（safety case）用结构化论证把安全目标、证据和假设联系起来。证据包括分析、测试、评审、工具报告、生产控制和现场监测。任何硬件替代、编译器升级、RTOS 配置变化或通信协议修改都可能影响既有论证，必须执行变更影响分析。

现场故障和近失事件应反馈到危害分析和诊断设计。安全生命周期直到产品退役才结束。

\section{工程实例：受控执行器}

考虑一个由位置传感器、控制器和功率驱动组成的线性执行器。普通功能接收目标位置并驱动电机；潜在危害是传感器、通信或软件故障导致执行器越过安全边界。

\subsection{Item 与危害}

系统边界包括位置传感器、控制 MCU、驱动级、电机、电源和上位机通信。示例安全目标定义为：检测到位置不可置信、控制任务失活或通信命令失效后，在 $100\,ms$ 内撤销驱动，并阻止自动重新使能。

该目标进一步分解为：
\begin{itemize}
  \item 控制器以不大于 $10\,ms$ 的周期验证位置范围、变化率和数据新鲜度；
  \item 独立硬件 watchdog 在 $40\,ms$ 内检测任务或时钟失活；
  \item 驱动使能具有默认关闭下拉，并可由独立安全输出撤销；
  \item 上位机命令包含序号、超时和目标范围，过期命令不得保持运动；
  \item 故障锁存后只允许经过受控确认和完整自检重新使能。
\end{itemize}

\subsection{FTTI 预算}

一种时间分配为：传感器诊断 $20\,ms$、状态确认 $10\,ms$、安全任务调度 $10\,ms$、驱动撤销 $5\,ms$、机械能量衰减 $35\,ms$，总计 $80\,ms$，保留 $20\,ms$ 裕量。

预算必须使用最坏任务相位和最坏负载测量。若诊断需要连续三个错误样本，其确认时间必须计入，而不能只记录单次采样周期。

\subsection{软件状态机}

安全状态机应独立于普通运动状态机：

\begin{lstlisting}[language=C,caption={执行器安全监督状态机（伪代码）}]
switch (safety_state) {
case SAFE_DISABLED:
    force_drive_off();
    if (authorized_reset() && all_self_tests_pass())
        safety_state = SAFE_READY;
    break;
case SAFE_READY:
    if (enable_request() && inputs_plausible())
        safety_state = SAFE_ACTIVE;
    break;
case SAFE_ACTIVE:
    if (!inputs_plausible() || command_expired() || !task_window_ok()) {
        force_drive_off();
        latch_fault();
        safety_state = SAFE_DISABLED;
    }
    break;
}
\end{lstlisting}

普通应用只能请求使能，不能直接写功率输出。安全监督器拥有最终使能权限，并使“故障后自动恢复”成为显式、可审查的策略。

\subsection{验证矩阵}

验证应分别注入传感器卡死、跳变、慢漂移、通信中断、任务死循环、时钟异常、驱动开路和驱动短路。每次测试测量故障发生到安全输出生效的时间，并检查故障锁存、复位原因和禁止自动重启。

这一实例的重点不是某个固定诊断阈值，而是从危害、安全目标、FTTI、架构分配、实现到故障注入形成可追踪证据链。

\section{检查清单}

\begin{itemize}
  \item 每个危害是否对应明确的安全目标、FTTI 和安全状态？
  \item 安全需求是否能够追踪到架构、实现和验证证据？
  \item 冗余通道的共因失效和独立性是否经过分析？
  \item 诊断机制是否针对具体失效模式，而不是笼统声明“有 CRC/看门狗”？
  \item 故障反应路径是否在目标硬件和最坏负载下测量？
  \item 工具、第三方软件、RTOS 和复杂器件是否具有明确的使用假设？
  \item 变更和现场数据是否持续更新安全论证？
\end{itemize}
