\chapter{Bootloader}
\label{chap:bootloader}

Bootloader（引导加载程序）负责把处理器从复位后的最小执行环境带到一个满足后续固件或操作系统入口契约的状态。
它通常还承担镜像选择、认证、恢复和现场诊断，但不应被理解为“在内核之前把所有硬件都初始化一遍”。
初始化范围越大，启动时间、攻击面、状态交接和版本兼容就越难控制。

本章聚焦 Bootloader 的技术选型、U-Boot、UEFI、Trusted Firmware-A、设备树及开发实践。
跨阶段内存所有权、A/B 状态机、Linux 入口、根文件系统与 PID~1 的完整工程闭环见第~\ref{chap:linux-boot-chain}~章；
构建和更新事务见第~\ref{chap:system-build-update}~章，产品安全生命周期见第~\ref{chap:security-lifecycle}~章。

\section{职责、边界与选型}

\subsection{最小职责集合}

一个可交付的 Bootloader 至少应明确完成以下工作：

\begin{enumerate}
  \item \textbf{建立可执行环境}：保存复位原因，建立栈、时钟、必要电源域和最早诊断通道；
  \item \textbf{装载后续阶段}：识别启动介质，在容量、地址和超时边界内读取镜像；
  \item \textbf{执行启动策略}：选择硬件配置、启动槽、正常或恢复路径，并限制重试；
  \item \textbf{验证输入}：检查格式、长度、产品兼容性、摘要、签名和安全版本；
  \item \textbf{构造交接}：传递 Device Tree/ACPI、内核命令行、内存地图、启动原因和槽位状态；
  \item \textbf{受控失败}：输出稳定错误码，保存证据，并进入经过认证的后备或恢复路径。
\end{enumerate}

Bootloader 不应隐式承担全部外设自检、复杂业务策略或无限交互式维修。
后一级不需要的外设应延迟初始化；安全关键策略不能只存在于可随意修改的环境变量中；
生产命令行也不能成为绕过镜像认证和访问控制的第二条启动路径。

选型不应只比较“支持多少命令或文件系统”。
还应比较启动 ROM 的加载限制、许可证和维护周期、长期密钥轮换、最坏启动时间、故障注入能力、现场恢复权限以及目标团队能否持续维护板级移植。

\subsection{启动场景不是一个布尔值}

至少区分冷启动、热复位、watchdog 复位、低功耗恢复、候选槽试启动、恢复启动和制造/维修启动。
每个场景都应定义允许的启动源、验证策略、硬件初始化范围、重试上限和可观察完成点。

例如，watchdog 复位后继续尝试同一损坏候选槽会形成重启风暴；热复位时无条件重复 DRAM 训练可能破坏仍在使用的保持内存；
维修启动若允许任意读取密钥或用户数据，则会把工厂接口变成永久后门。

\section{启动阶段与平台差异}

\subsection{阶段名称不能替代责任定义}

典型启动链可以抽象为：

  \caption{启动阶段的责任与输入约束}
  \begin{tabular}{p{27mm}p{48mm}p{62mm}}

    TPL/SPL/FSBL & 最小 pin、clock、PMIC、DRAM 与后续镜像装载 & 完整堆、所有驱动和用户配置可信 \\
    平台固件 & 特权级、安全状态、PSCI/SBI、可信服务 & 操作系统已建立页表和设备所有权 \\
    主 Bootloader & 配置选择、镜像验证、装载、恢复和 OS 入口 & 内核会清理所有未声明的 cache、中断和 DMA 状态 \\
    OS loader/内核 & 接管内存与设备模型，进入正式系统 & Bootloader 私有驱动状态仍可继续复用 \\
    \hline
  \end{tabular}
\end{table}

不同项目对 BL1、BL2、SPL、TPL 和 FSBL 的命名并不统一。
设计文档必须用“谁装载谁、运行在哪个地址和特权级、验证什么、失败后去哪里”描述阶段，而不能只写一个缩写。

\subsection{Arm A-profile}

Arm A-profile 处理器的复位入口、复位时异常级和安全状态由具体实现与 SoC 决定。
采用 Trusted Firmware-A 的平台通常由早期可信阶段装载 BL31，BL31 驻留在 EL3 并向非安全世界提供 PSCI 等运行时服务；
BL32 可承载 OP-TEE 等安全载荷，BL33 则是 U-Boot、UEFI 或其他非安全固件\cite{trusted-firmware-a-doc}。

U-Boot 并不固定“运行在 EL1”。
它可能由平台固件在 EL2 或 EL1 进入，最终必须按目标内核协议准备 CPU、MMU/cache、DTB 和次级 CPU 状态。
Arm64 Linux 的入口条件应以部署内核版本的文档为准\cite{linux-arm64-booting}。

\subsection{RISC-V}

RISC-V 的复位 PC 和最初特权级由平台定义。
常见链路是 Boot ROM/FSBL 在 M-mode 完成早期初始化，由 OpenSBI 提供 SBI 服务，再把 U-Boot 或 Linux 交给 S-mode。
设备树描述硬件并向后传递，但它不决定复位地址。

进入 Linux 前应确认 hart 状态、SBI 扩展、时间源、中断控制器、DTB 地址和保留内存均满足目标内核要求\cite{linux-riscv-booting}。
多 hart 平台还要定义次级 hart 是停驻、等待还是由固件管理，不能让多个 hart 同时执行同一初始化路径。

\subsection{UEFI 平台}

UEFI PI 实现常用 SEC、PEI、DXE 和 BDS 描述固件阶段；加载 OS loader 后进入 transient system load，调用
\texttt{ExitBootServices()} 后只剩规范允许的 Runtime Services。
Boot Services 是一组接口，不应被当作一个独立启动阶段\cite{uefi-spec}。

OS loader 获取 memory map 后，任何内存分配都可能改变 map key。
因此常见正确流程是获取足够大的缓冲区、再次取得最终 memory map，并在
\texttt{ExitBootServices()} 返回 \texttt{EFI\_INVALID\_PARAMETER} 时重新取图后有限重试。
无限重试或在退出后继续调用 Boot Services 都属于接口错误。

\subsection{MCU 启动}

MCU 的链路通常更短，但原子性要求并不更低。
跳转到应用前应验证向量表地址、初始栈指针、复位处理函数、对齐和镜像边界，并明确处理：

\begin{itemize}
  \item 关闭或转移中断，清理 pending 状态；
  \item 停止 Bootloader 私有 DMA、定时器和外设事务；
  \item 设置 VTOR 或平台等价寄存器；
  \item 规定时钟和 watchdog 由谁继承；
  \item 对 Cortex-M 使用架构规定的 Thumb 入口语义；
  \item 在双槽更新中先持久化尝试次数，再执行候选镜像。
\end{itemize}

MCUboot 提供镜像头、签名验证、升级策略和安全计数器等机制，但具体 swap、overwrite、direct-XIP 或 RAM-load
策略取决于 Flash 布局和所选版本\cite{mcuboot-doc}。

\section{U-Boot 工程实践}

\subsection{SPL、TPL 与主 U-Boot}

U-Boot 的主镜像通常依赖 DRAM 和较完整的驱动模型。
当 Boot ROM 的可加载尺寸、地址或介质能力不足时，可以先运行 SPL；某些平台还会在 SPL 之前增加 TPL，或使用其他受限阶段。
阶段尺寸不是固定的“64 KB”，必须以 SoC Boot ROM、片上 SRAM、镜像头和链接布局共同计算。

每个阶段都应单独记录：

\begin{itemize}
  \item 链接地址、装载地址、最大尺寸和对齐；
  \item 可用栈、堆、全局数据和临时缓冲区；
  \item 支持的启动源、驱动和镜像格式；
  \item 验证密钥、算法与安全版本策略；
  \item 失败码、重试次数和后备路径；
  \item 生成它的配置、工具链、DTS 和源码提交。
\end{itemize}

\subsection{可复现配置与构建}

U-Boot 使用 Kconfig、defconfig、设备树和板级代码共同定义产物。
推荐使用独立输出目录，并把最终展开配置而不只是 defconfig 纳入发布归档：

\begin{lstlisting}[language=bash,caption={U-Boot 独立输出目录构建示例}]
make O=out ARCH=arm CROSS_COMPILE=arm-none-eabi- myboard_defconfig
make O=out olddefconfig
make O=out -j8
\end{lstlisting}

发布 manifest 至少记录源码提交、补丁集、工具链摘要、\texttt{out/.config}、输入 DTS/overlay、签名密钥 ID、
生成的 SPL/TPL、主镜像、映射文件和最终封装镜像摘要。
构建目录中的 \texttt{u-boot.bin}、\texttt{u-boot.img}、\texttt{u-boot.itb} 和厂商打包文件语义不同，
烧录脚本必须引用明确产物而不是选择“最新的 bin 文件”。

私钥不应放入源码树或普通 CI artifact。
构建服务可以向受控签名服务提交待签摘要或无签名镜像，再把签名和证书链以可审计步骤注入最终产物。

\subsection{Driver Model 与设备树}

现代 U-Boot 使用 Driver Model 组织 uclass、device 和 driver，并可由设备树驱动绑定。
SPL 与主 U-Boot 的设备树和驱动集合可能不同；主镜像能识别某控制器，并不表示 SPL 也包含其时钟、pinmux、
存储和电源依赖。

板级移植应优先修正设备树和通用驱动，不要用大量板级 hook 重复描述硬件。
确需 fixup 时，应限制允许修改的节点和属性，记录修改原因，并对传给内核的最终 DTB 计算摘要。

\subsection{Standard Boot 与 bootflow}

较新的 U-Boot 可以通过 Standard Boot/bootflow 对启动设备、启动方法和发现结果建模\cite{uboot-doc}。
下列命令仅是启用相应配置后的诊断示例，实际名称和输出以目标版本为准：

\begin{lstlisting}[language=bash,caption={U-Boot bootflow 诊断示例}]
bootdev list
bootflow scan -lb
bootflow info
bootflow boot
\end{lstlisting}

生产策略不应依赖人工执行扫描结果。
应固定启动设备优先级、允许的文件系统和网络方法、超时、硬件匹配条件以及失败后是否继续尝试下一候选。
可移动介质和网络启动在开发阶段很方便，量产阶段若无需使用就应关闭，或要求物理条件与认证授权同时满足。

\subsection{装载地址与重叠检查}

内核、DTB、initramfs、解压工作区、U-Boot relocation、可信固件保留区、CMA、framebuffer 和远端核固件
必须共享一致的内存地图。
对区域 $i$ 定义基址 $B_i$、长度 $S_i$ 和末地址 $E_i=B_i+S_i$，任意两个同时有效区域 $i,j$ 应满足：

\begin{equation}
  E_i \le B_j \quad \text{or} \quad E_j \le B_i
\end{equation}

计算必须检查整数溢出，并使用镜像解压后的最坏尺寸而不是压缩文件大小。
Bootloader 应在复制、解压或启动前拒绝越界和重叠，构建系统也应对发布布局执行同一检查。

\subsection{FIT 镜像与配置绑定}

FIT 可以把内核、DTB、initramfs、配置与签名关系放入一个可描述容器。
关键不是“给文件加一个签名”，而是让签名覆盖实际选择的配置及所有能改变执行行为的对象。

\newpage
\begin{lstlisting}[language=dts,caption={FIT 配置与签名关系示意}]
/ {
    images {
        kernel {
            data = /incbin/("Image");
            type = "kernel";
            arch = "arm64";
            os = "linux";
            compression = "none";
        };
        fdt {
            data = /incbin/("myboard.dtb");
            type = "flat_dt";
            compression = "none";
        };
    };
    configurations {
        default = "conf-prod";
        conf-prod {
            kernel = "kernel";
            fdt = "fdt";
            signature {
                algo = "sha256,rsa2048";
                key-name-hint = "release";
                sign-images = "kernel", "fdt";
            };
        };
    };
};
\end{lstlisting}

示例只表达关系，算法、密钥长度、证书格式和节点语法必须与目标 U-Boot 版本和产品密码策略一致。
配置选择还应绑定产品 ID、板卡修订和安全版本，不能仅根据可由用户空间修改的文件名或环境变量决定。

\subsection{环境变量治理}

U-Boot 环境是可变持久化状态，不是天然可信的配置数据库。
设计时应明确：

\begin{itemize}
  \item 存储介质、擦除块、冗余副本、CRC 和 generation；
  \item 默认环境与持久化环境的优先级；
  \item 哪些变量允许现场修改，哪些必须由签名策略或编译配置固定；
  \item schema 版本、迁移规则和未知变量处理；
  \item 掉电发生在擦除、写入或切换副本时的恢复行为；
  \item 敏感信息是否会被 \texttt{printenv}、日志或导出命令泄露。
\end{itemize}

不要把防回滚下限、生产密钥、调试开关或任意 \texttt{bootcmd} 只保存在普通环境区。
环境损坏时应回到安全默认值，并保留稳定故障码；“恢复默认环境后自动开放网络 shell”不是安全恢复。

\subsection{量产命令面}

开发版常启用内存读写、任意地址跳转、USB 下载、网络启动和环境保存。
量产版应根据威胁模型裁剪命令，并把维护能力分为：

\begin{description}
  \item[无需授权的只读诊断] 版本、复位原因、验证结果和有限硬件状态；
  \item[物理授权诊断] 需要跳线、按钮、机箱开启或专用工装；
  \item[密码学授权操作] 绑定设备身份、能力、有效期或启动次数的签名授权；
  \item[永久禁止操作] 读取不可导出密钥、降低安全版本或执行未认证镜像。
\end{description}

隐藏命令名、缩短 autoboot 中断窗口或设置通用口令都不能替代授权设计。

\section{UEFI 与 GRUB}

\subsection{UEFI 对象和服务边界}

UEFI 通过 handle、protocol、device path、system table、Boot Services 和 Runtime Services 提供标准接口\cite{uefi-spec}。
固件与 OS loader 的关键契约包括：

\begin{itemize}
  \item memory map 中各区域类型、属性和页边界；
  \item image handle、loaded image protocol 和启动设备路径；
  \item ACPI/SMBIOS/Device Tree 等配置表；
  \item \texttt{GetVariable}/\texttt{SetVariable} 的属性、容量和认证要求；
  \item \texttt{ExitBootServices()} 前后的接口可用性；
  \item Runtime Services 映射和虚拟地址切换约定。
\end{itemize}

NVRAM 变量容量和写入寿命有限。
启动失败计数、日志和高频遥测不应无界写入变量区；变量更新还要处理空间不足、垃圾回收、认证时间戳和掉电。

\subsection{UEFI Secure Boot 密钥角色}

UEFI Secure Boot 常用以下授权对象：

\begin{itemize}
  \item Platform Key（PK）：控制平台所有权状态；
  \item Key Exchange Key（KEK）：授权更新允许/撤销数据库；
  \item \texttt{db}：允许的签名、证书或摘要；
  \item \texttt{dbx}：撤销的签名、证书或摘要。
\end{itemize}

\texttt{efibootmgr} 主要管理 \texttt{BootOrder}、\texttt{Boot\#\#\#\#} 等启动项，不是通用 Secure Boot 密钥数据库管理器。
密钥注册、轮换和撤销应使用平台支持的认证变量流程，并验证 setup/user mode、物理在场策略和失败恢复。

固件验证 EFI image 只是信任链的一段。
GRUB 配置、动态模块、内核、initramfs 和内核命令行若可被未授权替换，仍可能改变最终执行策略。

\subsection{GRUB 在 BIOS 与 UEFI 下的差异}

GRUB 2 由平台镜像、核心功能、模块和配置组成\cite{grub-manual}。
在传统 BIOS/GPT 系统中，\texttt{core.img} 通常需要 BIOS Boot Partition；
在 UEFI 系统中，固件从 EFI System Partition 加载 GRUB 的 EFI executable。
把 \texttt{core.img} 简单描述为“安装在 MBR 中”会忽略实际容量与平台差异。

\texttt{grub.cfg} 通常由发行版工具生成，手工修改生成文件容易在下次更新时丢失。
启用 Secure Boot 时还要确认 shim、GRUB、本地证书、模块加载策略和内核签名之间的责任边界；
允许从交互式命令行加载任意未签名模块会削弱前级验证。

\section{Trusted Firmware-A}

\subsection{BL 阶段映射}

Trusted Firmware-A（TF-A）是 Arm A-profile 平台可信固件的参考实现\cite{trusted-firmware-a-doc}。
常见阶段语义如下，但并非每个平台都会构建或使用全部阶段：

\begin{itemize}
  \item \textbf{BL1}：可信复位或早期阶段，很多 SoC 由厂商 Boot ROM 承担等价职责；
  \item \textbf{BL2}：Trusted Boot Firmware，装载并可认证后续镜像；
  \item \textbf{BL31}：驻留 EL3 的运行时固件，提供 PSCI 和平台 SMC 服务；
  \item \textbf{BL32}：可选安全载荷，例如 OP-TEE；
  \item \textbf{BL33}：非安全固件，例如 U-Boot、UEFI 或直接 OS loader。
\end{itemize}

镜像名称不能替代平台文档。
例如厂商 FSBL 可能负责 DRAM 并直接装载 BL31，FIP 中镜像组合也会随平台和 Trusted Board Boot 配置变化。

\subsection{构建与接口验证}

\begin{lstlisting}[language=bash,caption={TF-A 平台构建形式示意}]
make PLAT=<platform> \
     CROSS_COMPILE=aarch64-none-elf- \
     DEBUG=0 \
     all fip
\end{lstlisting}

发布时应固定平台、TF-A 提交、编译器、宏配置、FIP 工具版本、证书链和各 BL 镜像摘要。
只保存最终 \texttt{fip.bin} 会丢失“哪个 BL31、BL32 和 BL33 被组合”的证据。

Linux 启动成功也不足以证明平台固件接口完整。
还应验证 CPU hotplug、system reset、suspend、system off、SMC 并发、错误返回、共享内存 cache 一致性和受保护内存边界。
BL31 版本和能力应进入现场诊断信息。

\section{Device Tree 在 Bootloader 中的职责}

Device Tree 是固件向操作系统传递硬件视图的版本化 ABI，其通用格式与属性由 Devicetree Specification 定义，
设备细节还必须满足对应 binding\cite{devicetree-spec}。

\newpage
\subsection{地址单元与属性语义}

\begin{lstlisting}[language=dts,caption={地址单元和串口属性示意}]
/dts-v1/;

/ {
    #address-cells = <2>;
    #size-cells = <2>;

    memory@80000000 {
        device_type = "memory";
        reg = <0x0 0x80000000 0x0 0x40000000>;
    };

    serial@ff000000 {
        compatible = "ns16550a";
        reg = <0x0 0xff000000 0x0 0x1000>;
        clock-frequency = <24000000>;
        current-speed = <115200>;
        status = "okay";
    };
};
\end{lstlisting}

\texttt{clock-frequency} 表示设备输入时钟，不是串口波特率；波特率可由 \texttt{current-speed} 表达。
\texttt{reg} 的 cell 数由父节点的 \texttt{\#address-cells} 和 \texttt{\#size-cells} 决定；
\texttt{interrupts} 的 cell 格式则由中断控制器 binding 决定，不能复制一组三元组到所有平台。

\subsection{fixup、overlay 与最终证据}

Bootloader 常修改 \texttt{/chosen}、可用内存、MAC 地址、序列号和板卡 revision。
每个 fixup 应回答：

\begin{itemize}
  \item 原始数据来自 OTP、EEPROM、环境还是自动探测，可信度如何；
  \item 若数据缺失、校验失败或硬件不匹配，选择失败还是安全默认值；
  \item 属性是否位于镜像签名覆盖范围内；
  \item overlay 的适用硬件、优先级和冲突如何验证；
  \item 最终 DTB 摘要和所选配置如何记录。
\end{itemize}

DTB、overlay、Bootloader fixup 和内核 binding 必须作为一个兼容集合测试。
\texttt{dtc} 语法通过不表示 binding 正确，CI 还应运行目标内核 schema 的 \texttt{dt-validate} 或等价检查。

\section{安全启动、回滚与恢复}

\subsection{验证范围}

安全启动要求前一级在使用前授权后一级。
验证对象不仅是可执行代码，还包括能够改变执行行为的 DTB、initramfs、命令行策略、可加载模块、协处理器固件和恢复镜像。
只签名内核却允许替换 DTB 或 initramfs，会留下等价绕过路径。

验证至少应绑定：

\begin{itemize}
  \item 产品族、板卡修订、启动介质和硬件配置；
  \item 镜像类型、长度、装载范围、入口和组件摘要；
  \item 签名算法、密钥标识、证书或授权链；
  \item 安全版本、防回滚下限和兼容组件集合；
  \item 失败策略、恢复镜像身份和可输出的诊断信息。
\end{itemize}

\subsection{Verified Boot 与 Measured Boot}

Verified Boot 在执行前检查授权，不满足策略就拒绝执行。
Measured Boot 记录实际装载的组件和配置，供本地或远程证明使用，但它本身不一定阻止执行。
两者可以组合，度量事件日志必须与受保护测量寄存器和最终执行对象一致。

根文件系统完整性可以使用 dm-verity 等机制扩展信任链\cite{linux-dm-verity}，
但 verity root、数据块设备、命令行和错误行为也必须由已认证配置绑定。

\subsection{防回滚与版本提交}

合法签名的旧镜像仍可能包含已知漏洞。
Bootloader 应比较受保护的安全版本计数器，并只允许达到策略下限的镜像。
安全版本不必等同于产品版本：功能版本可以因兼容性回退，安全下限却不能退回已撤销版本。

不可逆计数器不应在新镜像第一次启动前过早推进。
推荐在候选镜像通过目标健康门槛且恢复策略仍成立后，再按平台能力提交新的安全下限。
计数器、槽位元数据和镜像写入之间的顺序必须经过逐阶段掉电测试。

\subsection{恢复不是旁路}

恢复镜像、ROM 下载、USB burning 和维修 shell 都属于信任边界。
恢复路径应：

\begin{itemize}
  \item 只接受适用于该设备且经过认证的恢复对象；
  \item 限制可读写区域和命令集合；
  \item 不允许降低安全版本或导出设备秘密；
  \item 区分修复系统、清除用户数据和退役设备；
  \item 保存操作者/授权、旧新版本、原因和结果；
  \item 在恢复完成后重新验证正式启动链。
\end{itemize}

平台固件韧性应覆盖保护、检测和恢复，而不是仅在校验失败后停机\cite{nist-platform-resiliency}。
密钥生命周期和调试授权详见第~\ref{chap:security-lifecycle}~章。

\section{启动槽位与状态元数据}

Bootloader 通常负责在 A/B 或多镜像方案中选择候选槽，并在执行前消耗有限尝试次数。
更新客户端负责写入和回读目标槽，用户空间健康服务负责确认成功；三者必须共享同一状态语义，不能各自维护一套“当前版本”。

\begin{table}[H]
  \centering
  \caption{Bootloader 参与的槽位状态转换}
  \begin{tabular}{p{31mm}p{43mm}p{64mm}}
    \hline
    当前状态 & 事件 & 原子动作与结果 \\
    \hline
    已知良好 A & B 已写入并回读校验 & 设置 B 为候选，写入有限尝试次数和新 generation \\
    候选 B & Bootloader 选择 B & 启动前持久化消耗一次尝试，再执行 B \\
    候选 B & 用户空间健康确认 & 将 B 标为成功，更新最后已知良好槽 \\
    候选 B & watchdog/启动失败 & 保存失败原因；仍有次数则重试，否则回退 A \\
    无可启动槽 & 验证或介质失败 & 进入受认证 recovery，不降低安全版本 \\
    \hline
  \end{tabular}
\end{table}

状态记录应具有 magic、格式版本、槽位状态、尝试次数、sequence/generation、CRC 或认证标签，并按介质原子写粒度保存冗余副本。
读取时选择完整且最新的副本；更新时先写旧副本、flush、回读验证，再允许它成为新状态。
完整数据结构和更新事务见第~\ref{chap:system-build-update}~章。

\section{Bring-up、调试与可观测性}

\subsection{建立最短可证伪路径}

新板 bring-up 推荐按以下顺序增加变量：

\begin{enumerate}
  \item 确认复位入口、最小栈和 GPIO/串口第一里程碑；
  \item 验证振荡器、主时钟、电源轨、复位和 pinmux；
  \item 以保守频率初始化 DRAM，并检查容量、地址别名和数据模式；
  \item 只启用一个启动介质，验证读超时、边界和错误返回；
  \item 装载一个尺寸与地址已知的最小后续镜像；
  \item 加入格式、摘要、签名和兼容性验证；
  \item 再加入网络、USB、显示、复杂文件系统和多启动策略。
\end{enumerate}

每一步都应有可观察成功点和稳定失败码。
一次同时打开 DDR 高频、多个存储驱动、网络和安全启动，会让“没有串口输出”无法区分时钟、内存、介质、签名还是入口状态错误。

\subsection{早期日志与复位证据}

早期日志至少记录：

\begin{itemize}
  \item 构建 ID、阶段、CPU/hart、时间戳来源和里程碑编号；
  \item 原始复位寄存器、规范化原因和启动计数；
  \item 启动源、硬件 revision、候选槽和剩余尝试；
  \item 镜像头版本、长度、密钥 ID、安全版本和验证结果；
  \item DRAM 训练档位、容量、降级状态和内存布局摘要；
  \item 最终 DTB/配置摘要与内核入口。
\end{itemize}

复位原因寄存器可能 read-to-clear，最早阶段应一次读取并向后传递。
日志不能输出私钥、完整设备凭据或可重放授权；安全启动失败可以输出稳定错误类别和密钥 ID，而不泄露敏感材料。

\subsection{调试工具的适用层次}

\begin{description}
  \item[示波器/逻辑分析仪] 观察电源、复位、strap、时钟、SPI/eMMC 总线和串口第一字节；
  \item[JTAG/SWD] 在串口可用前检查 PC、异常、寄存器、片上 SRAM 和 DDR 控制器；
  \item[串口] 记录连续阶段、命令输出和内核 early console；
  \item[网络/TFTP] 快速迭代已可信的后期镜像，不适合证明最早启动路径；
  \item[离线解析工具] 检查 ELF、map、FIT/FIP、DTB、分区表和签名链。
\end{description}

量产锁定后 JTAG/SWD 可能不可用，项目应提前准备认证调试、受控工程样机或签名诊断镜像。
不要等现场故障发生后才发现唯一证据通道已被永久关闭。

\subsection{watchdog 所有权}

Boot ROM、SPL、平台固件、U-Boot 和内核可能依次继承同一个 watchdog。
每次交接必须说明当前超时、是否暂停、下一喂狗期限和接管方。
长时间 DRAM 训练、镜像哈希、网络超时或解压不得靠无界喂狗掩盖卡死。

候选槽启动时，watchdog 复位应推进失败状态而不是无限重试同一镜像。
若硬件 watchdog 无法关闭，下一阶段必须在进入前已具备安全接管路径。

\section{启动性能优化}

启动时间应分段测量：

\begin{equation}
  T_{\mathrm{ready}} =
  T_{\mathrm{ROM}} + T_{\mathrm{early}} + T_{\mathrm{platform}} +
  T_{\mathrm{loader}} + T_{\mathrm{kernel}} + T_{\mathrm{userspace}}
\end{equation}

各阶段可能重叠，公式主要用于责任分解。
Bootloader 可使用稳定计时源或 bootstage，内核使用 printk 时间和 initcall trace，用户空间再记录核心功能 ready。
只测量“跳入内核”的时间会遗漏根文件系统、数据迁移和业务服务。

优化前应收集冷/热启动、候选/恢复启动、温度、电压、介质老化和网络状态下的 P50、P90、P99、最大值与失败率。
常见收益来自减少串行探测、固定不存在设备的超时、避免重复读取、选择合适压缩算法和延迟非关键外设。

不能通过跳过签名、内存边界检查、必要自检、watchdog 接管或过早确认 A/B 成功来制造更短数字。
压缩镜像是否更快取决于介质吞吐、CPU 解压速度、工作区和 cache；应测量端到端时间与峰值内存，而不是只比较文件大小。

\section{故障注入与验收}

\begin{table}[H]
  \centering
  \caption{Bootloader 最小故障注入矩阵}
  \begin{tabular}{p{38mm}p{46mm}p{54mm}}
    \hline
    场景 & 注入方式 & 期望结果与证据 \\
    \hline
    冷启动边界 & 最低/最高温度、电压和慢介质 & 在预算内启动或稳定失败，记录训练档位和阶段 \\
    环境/状态更新掉电 & 在擦除、写入、flush、切换时断电 & 选择完整副本，不启动未校验候选 \\
    镜像损坏 & 修改头、长度、数据或签名 & 在执行前拒绝，输出稳定验证错误 \\
    合法旧镜像 & 使用有效签名但低安全版本 & 防回滚拒绝，不破坏当前可启动槽 \\
    硬件错配 & 错误 DTB、板卡 revision 或容量 & 兼容检查拒绝，不访问越界设备 \\

    watchdog 复位 & 在各里程碑停止喂狗 & 复位原因可追踪，候选尝试次数有界 \\
    正式槽损坏 & 破坏内核、rootfs 或元数据 & 进入受认证 recovery，不开放旁路命令 \\
    \hline
  \end{tabular}
\end{table}

验收不应只在一块开发板上重复正常上电。
至少覆盖硬件修订、启动介质批次、空白/满载/老化介质、冷/热/watchdog 复位、多次掉电、错误签名、撤销密钥、旧安全版本和恢复授权。
自动化方法见第~\ref{chap:test-automation-hil}~章，介质持久化语义见第~\ref{chap:storage-reliability}~章。

\section{交付检查清单}

\begin{itemize}
  \item 每个启动阶段的装载者、地址、尺寸、入口、特权级和失败路径是否明确？
  \item Boot ROM strap、后备启动源和下载模式是否在量产状态下验证？
  \item SPL/TPL、TF-A、U-Boot、DTB 和签名配置能否从锁定输入复现？
  \item 装载地址是否按解压后最大尺寸执行溢出与重叠检查？
  \item 传给内核的最终 DTB、命令行和内存地图是否属于认证与审计范围？
  \item U-Boot 环境是否具有冗余、generation、掉电恢复和安全默认值？
  \item 量产命令面是否移除任意执行、未认证刷写和秘密导出能力？
  \item Secure Boot 是否覆盖 DTB、initramfs、模块、外设固件和恢复镜像等真实策略输入？
  \item 密钥轮换、撤销、防回滚和不可逆计数器推进顺序是否演练？
  \item A/B 尝试次数是否在启动前原子消耗，健康确认是否来自产品关键功能？
  \item 冷启动、热复位、watchdog、低功耗恢复和维修启动是否具有不同且可测试的状态契约？
  \item 早期日志能否关联构建 ID、复位原因、启动槽、验证结果、DRAM 档位和最终入口？
  \item watchdog 是否在每次阶段交接时明确所有权和接管期限？
  \item 启动时间指标是否覆盖尾延迟、环境边界、失败率和核心功能 ready？
  \item 恢复路径是否受认证、保留审计，并且不会降低安全版本或泄露设备秘密？
\end{itemize}
