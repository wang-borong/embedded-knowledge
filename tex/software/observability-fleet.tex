\chapter{嵌入式可观测性与现场运维}
\label{chap:observability-fleet}

实验室中可连接 JTAG 和示波器，现场设备通常只能提供有限日志、指标和远程诊断。可观测性必须在设计阶段建立，使开发者能够从外部输出推断系统内部状态，同时控制存储、带宽、隐私和安全风险。

\section{日志、指标与追踪}

三类信号解决不同问题：
\begin{description}
  \item[日志] 记录离散事件及上下文，适合解释发生了什么；
  \item[指标] 记录计数、gauge、histogram 和水位，适合趋势与告警；
  \item[追踪] 关联一次事务跨进程、跨核和跨设备的阶段，适合定位延迟与因果关系。
\end{description}

只有自由文本日志会难以聚合，只有指标会缺少故障上下文。关键事务应同时具有 request/transaction ID、阶段指标和有限事件日志。

\section{结构化事件}

结构化事件应包含稳定 event ID、严重级别、单调时间、可选实时时间、组件、版本和字段。消息文本可以变化，event ID 和字段语义应保持兼容。

\begin{lstlisting}[language=C,caption={设备事件的逻辑结构}]
struct device_event {
    uint32_t schema_version;
    uint32_t event_id;
    uint64_t monotonic_ns;
    int64_t  realtime_ns;
    uint32_t component_id;
    uint32_t severity;
    uint64_t transaction_id;
    uint8_t  payload[EVENT_PAYLOAD_MAX];
};
\end{lstlisting}

ISR 和故障处理路径不应执行格式化、文件 I/O 或网络发送，可以写入固定长度的 lock-free/per-CPU ring，再由后台任务编码和持久化。

\section{日志容量与寿命}

日志必须有速率、容量和保留策略。重复错误应聚合为首次事件、计数和周期摘要，避免单一故障写满存储。

持久日志需要考虑写放大和掉电。高频调试日志可保存在 RAM ring，仅在故障触发时冻结并导出；审计和安全事件则需要受保护、可检测篡改的持久记录。

日志等级不应由远端永久切换到无限 verbose。诊断模式应有时间限制、权限控制和自动恢复。

\section{关键指标}

指标应直接对应资源和故障预算，例如：
\begin{itemize}
  \item 任务/线程最大延迟、队列水位和丢弃计数；
  \item 内存、fd、DMA buffer 和存储剩余；
  \item ECC corrected/failed、I/O error 和文件系统只读切换；
  \item 网络重连、丢包、RTT 和时间同步 offset；
  \item 温度、降频、功耗状态和唤醒原因；
  \item watchdog、崩溃、回滚和启动失败次数。
\end{itemize}

仅报告当前值会遗漏峰值，关键资源应保存 high-water mark 和 histogram。计数器需要定义重启、回绕和持久化语义。

\section{跨层事务追踪}

控制命令、媒体帧、OTA 和生产操作可以使用 transaction ID 关联用户空间、内核、远端核和云端事件。跨设备追踪还需要时间同步和时钟不确定度。

追踪点应围绕状态边界，而不是给每个函数打印 enter/exit。高频路径使用采样或硬件 trace，避免观测本身改变实时性。

\section{崩溃证据}

MCU HardFault 应保存寄存器、堆栈、任务、复位原因和固件版本；Linux 保存 pstore/ramoops、core dump、内核 oops 和服务状态。所有地址解析都依赖完全匹配的 ELF 和符号。

崩溃区写入必须有界且抗二次故障。若 fault handler 再次异常，应保留首次故障的最小头部，而不是反复覆盖。

\section{现场诊断包}

诊断包可以包含版本 manifest、配置摘要、日志片段、指标、进程/线程状态、网络配置和崩溃信息。生成过程必须设置大小和时间上限，并在收集失败时保留部分结果。

敏感密钥、token、用户内容和完整内存不应默认进入诊断包。字段应分级，导出前执行脱敏和访问授权。

\section{远程设备管理}

设备管理通常包含 inventory、配置、命令、OTA、健康和证书生命周期。控制面必须区分期望状态与设备报告状态，并能处理设备长时间离线、重复命令和服务端重试。

远程命令应具有 ID、签名或认证通道、过期时间、适用设备条件和结果回执。任意 shell 不应作为常规运维接口；诊断操作应建模为受限、可审计命令。

\section{分批发布与回滚}

OTA 应按实验设备、内部设备、小比例 canary 和逐步扩大批次发布。每一阶段根据启动成功率、崩溃率、关键功能和资源指标设置自动暂停门槛。

设备回滚不等于云端配置和数据自动回滚。发布系统需要记录固件、模型、配置 schema 和服务端能力的兼容关系。

\section{隐私与数据治理}

遥测应遵循最小收集、目的限定和保留期限。设备唯一身份、位置、音视频和用户操作可能属于敏感数据。数据上传前应明确字段、采样率、存储区域和访问角色。

删除设备或用户账户时，还需要处理云端备份、诊断包和离线队列。隐私策略必须落实为实际数据生命周期，而不是只存在于用户协议。

\section{离线与弱网}

现场设备可能长期离线。遥测队列应有容量、优先级和淘汰策略，安全事件和升级结果不能被大量普通指标挤出。重连后应限速上传，避免占满业务链路。

设备本地必须能够完成核心诊断和恢复，不应把云端在线作为进入安全状态或回退的必要条件。

\section{运维安全}

远程诊断、日志等级、抓包和固件下载都扩大攻击面。操作需要最小权限、短期授权、审计和速率限制。服务端凭据泄漏时，设备端仍应拒绝不满足本地安全策略的危险操作。

现场维修模式应由物理动作、设备状态和授权共同开启，并自动超时。维修完成后验证调试口、临时账户和诊断服务已经恢复量产策略。

\section{检查清单}

\begin{itemize}
  \item 日志、指标和 trace 是否各自解决明确问题？
  \item 高频故障是否聚合并受到容量和写入速率限制？
  \item 崩溃信息是否能关联完全匹配的符号和版本？
  \item 诊断包是否有界、可部分成功并执行敏感数据过滤？
  \item 远程命令是否具有 ID、过期、授权、审计和幂等语义？
  \item OTA 是否分批发布并由设备健康指标自动暂停？
  \item 离线队列、隐私、数据保留和维修模式是否有明确策略？
\end{itemize}
