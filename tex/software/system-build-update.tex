\chapter{系统构建、存储与 OTA}
\label{chap:system-build-update}

嵌入式 Linux 产品不是内核、根文件系统和应用的简单拼接，而是一组具有版本、依赖、启动顺序和恢复策略的系统镜像。
本章说明如何把工具链、Bootloader、内核、设备树、固件、根文件系统和应用组织成可复现、可升级、可恢复的交付物。

\section{交叉编译与系统 ABI}

交叉工具链至少包含编译器、汇编器、链接器、C 库、头文件和目标 sysroot。
工具链三元组只描述部分目标属性，不能单独保证二进制兼容。工程还应锁定：
\begin{itemize}
  \item 目标架构、指令扩展、浮点 ABI 和字节序；
  \item 内核 UAPI 头文件版本与最低内核要求；
  \item glibc、musl 或其他 C 库及动态加载器路径；
  \item C++ ABI、异常和运行时库版本；
  \item 链接方式、RPATH/RUNPATH 和符号版本策略。
\end{itemize}

sysroot 应由构建系统管理，不应直接指向某台开发板的根文件系统。否则未声明的头文件和库会造成不可复现构建，并可能把目标机上的临时状态带入发布产物。

\section{构建输入图与宿主隔离}

发布构建应被看作一张有向输入图，而不是一条只在某台 CI 主机上可运行的 shell 历史。源码、补丁、配置、工具链、主机构建工具、预生成固件和签名策略都属于输入；Bootloader、内核、DTB、固件、rootfs、符号文件、SBOM 和更新包则是具有可追踪关系的产物。

每个不可现场重建的输入至少应记录：
\begin{itemize}
  \item 稳定名称、版本或源码提交，以及内容摘要；
  \item 获取位置、许可证、供应方和镜像仓库；
  \item 选择该版本的理由、已知补丁和替换触发条件；
  \item 由哪个构建步骤消费，以及进入哪些最终产物；
  \item 是否允许网络获取、是否需要凭据、是否属于出口或客户限制材料。
\end{itemize}

宿主工具和目标工具必须分开管理。主机上的 \texttt{pkg-config}、Python 模块、压缩器或镜像工具版本变化，同样可能改变目标产物。构建环境应显式固定 \texttt{PATH}、locale、时区、umask、并行度相关非确定性和临时目录策略；目标编译不得意外搜索宿主 \texttt{/usr/include} 或 \texttt{/usr/lib}。

推荐把流水线拆为“获取并校验输入、离线构建、组装镜像、内容复核、生成元数据、签名与发布”几个边界。普通编译 worker 不应长期持有发布签名密钥；签名步骤只接收已经复核的摘要和受控元数据，并输出可审计签名记录。

\section{根文件系统组成}

根文件系统至少需要提供动态加载器、运行库、设备节点管理、初始化系统、配置、日志和应用。
BusyBox 适合资源受限系统；systemd 提供完整的服务依赖、日志和设备管理能力。选择应基于启动、维护和资源需求，而不是仅比较镜像大小。

\subsection{启动与服务管理}

用户空间第一个进程 PID 1 负责系统初始化和孤儿进程回收。服务定义应明确依赖、启动超时、失败重启、资源限制和安全权限。
关键应用不应依靠固定延时等待设备，而应依赖稳定的设备事件、socket 激活、服务依赖或显式健康条件。

\subsection{只读系统与可写数据}

将系统软件与产品数据分离可以降低掉电损坏和升级失败风险。常见设计是只读系统分区配合独立数据分区，必要时使用 OverlayFS 提供有限的可写视图。

必须明确以下数据的归属和生命周期：
\begin{itemize}
  \item 出厂配置与设备唯一身份；
  \item 用户配置和运行数据库；
  \item 日志、崩溃转储和升级状态；
  \item 可重新生成的缓存；
  \item 密钥、证书和防回滚计数器。
\end{itemize}

\section{Buildroot 与 Yocto Project}

Buildroot 通过 Kconfig 和包描述生成工具链、根文件系统、内核和 Bootloader，结构直接，适合单一产品或较集中配置的系统\cite{buildroot-manual}。
Yocto Project/OpenEmbedded 使用 recipe、layer 和共享状态缓存管理复杂发行版，适合多产品复用、包级许可追踪和长期产品线\cite{yocto-mega-manual}。

二者不是按项目规模机械选择。评估时应考虑：
\begin{itemize}
  \item 产品数量及公共组件复用程度；
  \item 是否需要运行时包管理和多种镜像组合；
  \item 供应商 BSP 与社区层的质量；
  \item 构建时间、缓存、CI 和团队学习成本；
  \item 许可证报告、SBOM 和长期安全维护要求。
\end{itemize}

无论采用何种系统，都应把板级差异、产品差异和本地补丁分层管理，禁止长期直接修改下载后的上游源码树。

\section{配置分层与补丁治理}

配置层次应让“公共能力”和“具体产品选择”可被分别审查。一个常见顺序是：上游默认、SoC/BSP、板卡、产品、部署地区或客户变体。后层只能覆盖有明确业务理由的项，最终合并后的内核配置、Device Tree、包选择和服务策略必须作为发布证据保存，不能只保存若干输入 fragment。

Buildroot 的 \texttt{defconfig}、\texttt{BR2\_EXTERNAL} 和 rootfs overlay，或 Yocto 的 layer、distro/machine 配置与 image recipe，都应避免复制整份上游配置后长期漂移。对同一硬件的产品差异，优先通过可组合特性和小型配置片段表达；若条件分支已经无法解释最终结果，应拆分明确的产品基线。

本地补丁队列至少记录：
\begin{itemize}
  \item 原始问题、受影响版本和最小复现；
  \item 补丁来源、维护责任人及是否已提交上游；
  \item 安全、ABI、实时、功耗和硬件兼容影响；
  \item 可删除补丁的上游版本或其他退出条件；
  \item 每次 BSP、工具链或主版本升级时必须重跑的测试集合。
\end{itemize}

“补丁可以干净应用”只证明文本上下文仍匹配，不证明语义仍正确。更新厂商 BSP 时，应重新检查寄存器默认值、Device Tree binding、固件接口、编译器告警和启动链，而不是只处理冲突块。

\section{存储介质与文件系统}

\subsection{NOR、NAND 与管理型闪存}

NOR Flash 支持随机读取并常用于启动固件；原始 NAND 密度高，但需要坏块管理、ECC 和磨损均衡；eMMC、SD 和 UFS 在器件内部提供闪存转换层，对主机表现为块设备。

块设备文件系统不能直接用于原始 NAND。Linux MTD 提供原始闪存抽象，UBI 在其上处理擦除块映射、坏块和磨损均衡，UBIFS 再提供文件系统语义。
分层关系和镜像生成参数必须与实际页大小、擦除块大小、OOB 和 ECC 布局一致。

\subsection{文件系统选择}

\begin{description}
  \item[ext4] 适合通用块设备，工具成熟并支持日志；
  \item[SquashFS] 压缩只读，适合不可变系统镜像；
  \item[EROFS] 面向高性能只读镜像，并支持压缩；
  \item[UBIFS] 面向 UBI 之上的原始 NAND；
  \item[tmpfs] 使用内存保存临时数据，重启后丢失；
  \item[OverlayFS] 把只读下层与可写上层组合为统一视图。
\end{description}

文件系统有日志不代表应用事务必然掉电安全。应用必须理解写回、\texttt{fsync()}、目录项持久化、重命名原子性和存储设备缓存策略。

\section{镜像与分区设计}

镜像清单应明确 Boot ROM 可见区域、Bootloader、环境或元数据、内核、设备树、根文件系统、恢复系统和持久化数据区。
固定偏移、分区表、卷名和 UUID 都属于升级兼容接口。

分区设计应为以下需求保留空间：
\begin{itemize}
  \item 镜像增长与文件系统元数据；
  \item 双系统或恢复镜像；
  \item 崩溃转储与升级暂存；
  \item 设备身份和工厂校准数据；
  \item 坏块、磨损和生产差异裕量。
\end{itemize}

发布流程应生成机器可读 manifest，记录每个组件的版本、摘要、大小、地址、构建来源和签名信息。

\subsection{镜像的只读检查}

发布前应从最终磁盘镜像重新解析分区表并检查文件系统内容。Linux 可以用 loop 设备把镜像分区映射为块设备，但检查过程应默认只读，并确保异常退出时解除映射：

\begin{lstlisting}[language=bash,caption={磁盘镜像的只读挂载检查}]
loopdev=$(sudo losetup --find --show --partscan final.img)
mount_dir=$(mktemp -d)
sudo mount -o ro,noload "${loopdev}p2" "${mount_dir}"

verify-rootfs-policy "${mount_dir}"
sudo umount "${mount_dir}"
sudo losetup --detach "${loopdev}"
rmdir "${mount_dir}"
\end{lstlisting}

ext4 使用 \texttt{noload} 可以避免只读检查时回放日志而修改镜像。自动化脚本还应使用 trap 清理 loop 设备，并校验分区 UUID、卷标、文件权限、动态链接器、服务单元和版本 manifest。

\section{镜像兼容契约}

镜像不是只由“版本号更大”决定能否安装。发布 manifest 应显式描述至少以下兼容轴：产品族、板卡修订范围、存储类型与容量、启动方案、最低 Bootloader/安全固件版本、内核与 DTB 组合、外设固件版本、数据 schema 以及安全版本计数。

\begin{lstlisting}[language=C,caption={镜像兼容清单的逻辑字段}]
struct image_compatibility {
    char product_id[32];
    uint16_t manifest_version;
    uint16_t hardware_min;
    uint16_t hardware_max;
    uint32_t minimum_boot_abi;
    uint32_t data_schema_read_min;
    uint32_t data_schema_write;
    uint64_t security_version;
    uint8_t payload_digest[32];
};
\end{lstlisting}

Device Tree 的 \texttt{compatible} 字符串只描述设备匹配的一部分，不能替代整机兼容矩阵。Bootloader、内核、DTB、rootfs 和协处理器固件若允许独立更新，必须声明可支持的组合窗口；若只能作为整体工作，则应由同一签名 manifest 原子绑定，拒绝任意混装。

兼容判断应在写入前完成，并在启动后再次把实际硬件、启动槽和已加载组件与 manifest 对照。前置检查防止明显误刷，启动后检查则能发现 Bootloader 选择了旧 DTB、工厂分区残留旧固件或槽位元数据损坏等组合错误。

\section{只读完整性与恢复边界}

只读根文件系统可以进一步使用 dm-verity 等机制按 Merkle 树校验块内容\cite{linux-dm-verity}。根哈希必须由受信任启动链或签名元数据保护；若攻击者可以同时替换镜像和根哈希，运行时校验没有建立新的信任边界。

完整性校验发现损坏并不等于系统能够恢复。产品还应定义：校验失败时是否切换备用槽、进入恢复系统、只开放诊断，还是保持特定安全输出。可写配置、数据库、日志和密钥不应被伪装成只读系统的一部分；它们需要独立的完整性、备份、迁移和寿命策略。

恢复镜像应尽量小、依赖少并采用独立验证路径。它至少能够识别正式镜像摘要、导出受控诊断、重建启动元数据和安装完整签名包，但不应默认暴露任意 shell、未认证网络刷写或通用密钥读取能力。

\section{可复现构建与软件物料清单}

可复现构建要求相同源码、配置、工具链和输入能够生成内容一致或可解释差异的产物\cite{reproducible-builds}。
工程应锁定源码提交、下载摘要、容器或构建环境、工具链版本和配置，并消除时间戳、路径和未排序输入等非确定性来源。

软件物料清单（Software Bill of Materials, SBOM）至少应列出组件、版本、许可证、来源和依赖关系。
SBOM 不是构建结束后人工整理的表格，而应由实际依赖图生成，并与镜像版本关联，用于许可证审查和漏洞响应。SPDX 等格式提供机器可读交换模型\cite{spdx-spec}；发布时还要固定所用规范版本、文档命名空间和组件标识规则，避免后端把同一组件拆成多个身份。

至少应执行一次与日常增量构建隔离的重建：清空工作目录和共享状态之外的隐式输入，在受控环境中重新生成产物，再按组件比较摘要。若最终镜像不一致，应先定位差异来自文件内容、压缩顺序、时间戳、签名随机性还是仅容器元数据，而不是简单把产物加入“允许差异”列表。

内容可复现与来源可信是两个不同问题。构建 provenance 应记录构建者身份、输入摘要、构建定义和输出摘要，并由受控构建服务签名；SLSA 给出了供应链 provenance 与分级控制的通用框架\cite{slsa-spec}。provenance 不能证明源码没有缺陷，但能减少“发布物究竟由什么产生”的不确定性。

发布归档除安装镜像外，还应包含未剥离符号或可定位符号包、源码与许可证对应关系、构建日志、配置、SBOM、provenance、签名元数据和验证报告。现场崩溃若只能拿到地址，却找不到完全匹配的 build ID 与符号，构建成功也无法支持产品维护。

\section{OTA 更新模型}

可靠更新系统至少具有真实性、完整性、原子切换、掉电恢复、防回滚和可观测状态。
下载成功不等于更新成功；系统必须在重启后验证新系统健康，再把候选版本标记为已确认。

\subsection{更新事务状态}

更新客户端应把流程建模为可恢复事务，而不是一个百分比。至少区分“元数据已验证、载荷下载中、载荷已暂存、目标写入中、目标已校验、等待试启动、等待健康确认、已确认、失败待处理”等状态，并为每个状态定义重启后的幂等动作。

状态记录必须与外部动作按明确顺序持久化。例如只有目标槽内容已经回读校验后，才能把它登记为可试启动候选；如果状态先提交而数据仍在设备缓存中，突然掉电可能让 Bootloader 启动不完整镜像。下载断点、块写入进度和最终槽位状态的持久化粒度可以不同，但都应有校验、generation 和旧记录回退路径。

失败分类至少区分网络、签名/策略、空间不足、介质 I/O、安装器、试启动、健康确认和服务器撤销。否则现场只能看到“更新失败”，无法决定应该重试下载、隔离存储、回滚版本还是停止整个发布批次。

\subsection{A/B 更新}

A/B 模型维护活动槽位和非活动槽位。更新写入非活动槽位，校验完成后仅修改少量启动元数据切换候选槽位。
Bootloader 维护尝试次数；新系统在完成关键自检后确认启动，否则回退到上一个已知良好版本。

启动状态机至少应区分：
\begin{itemize}
  \item 已确认的活动版本；
  \item 已写入但尚未尝试的候选版本；
  \item 正在试启动且剩余尝试次数有限的版本；
  \item 验证失败或被撤销的版本；
  \item 恢复模式。
\end{itemize}

状态元数据必须考虑原子写、冗余副本、校验和以及介质擦写粒度。

\subsection{A/B 的实现契约}

一个可落地的 A/B 方案需要 Bootloader、内核命令行、更新客户端和健康确认服务共享同一组最小状态。推荐状态字段包括：

\begin{lstlisting}[language=C,caption={冗余启动控制块的逻辑结构}]
struct boot_control {
    uint32_t magic;
    uint16_t format_version;
    uint8_t  active_slot;
    uint8_t  candidate_slot;
    uint8_t  attempts_left[2];
    uint8_t  successful[2];
    uint64_t sequence;
    uint32_t crc32;
};
\end{lstlisting}

介质上保存两个副本。读取时选择 CRC 正确且 \texttt{sequence} 最大的副本；更新时先写较旧副本，刷新介质缓存并回读校验，再把它作为新版本。控制块不能与大镜像共用一次非原子擦写操作。

更新客户端的基本流程如下：

\begin{enumerate}
  \item 验证签名、产品型号、硬件修订、版本和防回滚计数；
  \item 选择非活动槽，并确认当前根文件系统未从该槽启动；
  \item 以分块方式写入镜像，每块处理短写、I/O 错误和取消；
  \item 对块设备中的最终内容重新计算摘要，而不是只校验下载文件；
  \item 写入候选槽、尝试次数和新序列号，然后重启；
  \item Bootloader 每次试启动前递减尝试次数；
  \item 用户空间完成关键设备、数据分区和核心服务自检后，将当前槽标记为成功；
  \item 尝试耗尽仍未确认时，Bootloader 自动选择上一个成功槽。
\end{enumerate}

\begin{lstlisting}[language=bash,caption={健康确认服务的最小策略（伪代码）}]
current_slot=$(read-kernel-cmdline-slot)
wait-critical-services --timeout 60
check-data-mount --read-write
check-required-devices
bootctl mark-successful "${current_slot}"
\end{lstlisting}

“系统启动到登录界面”通常不足以确认成功。健康门槛应包含产品不可缺少的设备、服务和数据访问，但也不能依赖外部云服务永久可达，否则网络故障会导致无意义回滚。

\subsection{Buildroot 中的更新集成}

Buildroot 工程可以在 \texttt{BR2\_EXTERNAL} 中维护分区描述、更新客户端 package、健康服务和 post-image 脚本。post-build 只修改目标根文件系统，post-image 负责生成分区镜像、manifest 与签名；二者不应混用主机临时文件和目标文件。

推荐把构建结果拆分为不可变输入：\texttt{bootloader.bin}、\texttt{kernel.itb}、\texttt{rootfs.squashfs}、分区表描述和签名元数据。A/B 两个系统槽可以引用相同构建产物，但必须具有独立分区标识；持久化数据区不得复制到更新包中。

\subsection{更新框架与产品责任}

RAUC、SWUpdate、Mender、OSTree 等框架可以提供签名包、槽位写入或内容寻址能力。以 RAUC 为例，其 bundle、slot 与 Bootloader 状态集成可减少重复实现\cite{rauc-doc}。但框架不会替产品自动决定哪些服务构成健康、数据迁移能否回退、硬件变体是否兼容、执行器何时安全停机或现场密钥如何轮换。

选择框架时应验证其失败语义而不只比较功能表：写入被取消时槽位是什么状态，Bootloader 环境损坏如何处理，外部固件和 rootfs 能否组成一个安装事务，安装 hook 以什么权限运行，日志是否足以重建一次失败更新。若产品在框架之外又维护一套平行状态机，两者必须有唯一权威状态和一致恢复规则。

\subsection{差分、流式与空间预算}

差分包减少下载量，但把正确性绑定到精确基线。客户端必须验证当前基线摘要，而不能只比较版本字符串；重建完成后仍要对最终目标槽整体计算发布摘要。差分算法还会消耗暂存空间、RAM 和 CPU，最坏空间应同时计入旧块、新块、补丁、文件系统 copy-on-write 和日志。

流式安装可以减少双份暂存，但下载中断会留下部分写入的非活动槽。恢复时必须能够安全重写或继续，且永远不得把活动槽当作临时空间。对原始 NAND，还要考虑坏块变化使逻辑映射与服务器端假设不同；对管理型闪存，应把持续写入、设备 cache flush 和热/电源预算纳入测试。

更新期间的 watchdog、实时控制和电源管理也需要契约。擦除或校验不能无界阻塞关键健康路径；若业务运行时不允许更新，系统应先进入明确维护状态，而不是依赖“此时通常没有负载”。

\subsection{更新包与信任元数据}

更新包应签名并绑定产品型号、硬件修订、版本、依赖和载荷摘要。
仅给镜像附加单一长期签名密钥难以支持密钥轮换和职责分离，可以参考 TUF 的根、目标、快照和时间戳角色设计\cite{tuf-spec}。

更新客户端必须拒绝错误产品、依赖不满足、签名无效、元数据过期或低于安全版本计数器的载荷。
传输层加密不能替代离线可验证的更新签名。

根信任密钥应支持离线保管、阈值授权、轮换和撤销。在线发布服务通常只持有作用域受限的短期目标密钥；根角色变更应要求旧根与新根共同认可，避免单次在线凭据泄漏永久接管设备。设备时钟不可信时，元数据过期策略还需定义可信时间来源或有界例外，不能静默永久忽略过期。

\section{分批发布与停止条件}

设备端原子更新只解决单机一致性，不能替代车队级发布控制。发布计划应按实验设备、内部设备、低风险 canary、区域或硬件批次逐步扩大，并为每批定义观察窗口、最小样本量、成功率、启动回退率、关键业务错误、资源回归和人工投诉门槛。

控制面至少保存 campaign ID、目标版本、设备当前/期望版本、尝试次数、最后阶段和稳定错误码。设备上报“版本已下载”不能被统计为安装成功；服务器下发“回滚”也不能被统计为已恢复，必须等待设备确认实际启动槽和健康状态。

停止条件应在发布前确定。例如签名或型号错误应立即停止；少量网络失败可以重试；启动回退率、数据迁移错误或执行器异常超过阈值则暂停扩大并保护现场证据。自动回滚必须确认旧软件仍能读取新数据，且回滚不会违反已提高的安全版本计数。现场观测和分批策略可结合第~\ref{chap:observability-fleet}~章的方法。

\section{恢复、返厂与重新配置}

恢复路径应覆盖三类状态：正式系统仍能运行但应用损坏、正式系统无法启动但恢复环境可用、启动链或存储元数据已经损坏。每类状态都要说明触发方式、认证要求、能够保留的证据、允许执行的操作和退出条件。

“恢复出厂设置”必须定义实际擦除范围。用户配置、业务数据库、网络凭据、设备证书、校准、序列号、防回滚计数器和故障日志具有不同生命周期，不能用一次递归删除表达。设备转售、维修和报废还需与介质清除及身份退役策略一致。

返厂工具写入的镜像也应经过正式兼容和签名检查，并记录操作者、设备身份、旧/新版本和原因。若维修模式可以绕过安全启动或防回滚，它就成为高价值信任边界，必须采用物理授权、短期凭据或受控工装，而不能靠隐藏命令保护。

\section{配置与数据迁移}

系统软件可以回滚，但持久化数据格式可能已经升级。每个版本都应明确配置 schema、可读版本范围、写出版本、迁移方向、幂等性和失败恢复策略。
不可逆迁移会破坏 A/B 回退能力，常见解决方案是向前兼容读取、延迟提交迁移或对关键数据使用版本化副本。

推荐采用 expand/migrate/contract 思路：先让新旧软件都能理解扩展后的兼容格式，再后台迁移已有记录，只有候选系统确认并且回滚窗口关闭后，才删除旧字段或执行不可逆压缩。迁移进度应具有 generation 和断点恢复，重复执行不会重复扣费、重复创建对象或丢失旧索引。

数据备份必须在与主数据独立的故障域中验证恢复。把数据库复制到同一损坏文件系统的另一个目录不构成可靠备份。密钥、设备身份和工厂校准通常不应随普通用户数据回滚；它们需要单独版本和访问控制，并在恢复后验证与硬件身份仍匹配。

对跨版本运行的集群或主从设备，还应规定协议和数据 schema 的滚动兼容窗口。服务器先升级、设备后升级与设备离线数月后再上线，都是正常生命周期场景，不能只测试实验室中相邻两个版本同步切换。

\section{构建与更新验收}

\begin{itemize}
  \item 是否能从干净环境仅依据锁定输入生成发布镜像？
  \item 主机工具、网络下载和签名边界是否受控，能否说明每个产物的输入图？
  \item manifest、SBOM、provenance、许可证报告和符号文件是否与镜像版本一一对应？
  \item 硬件、Bootloader、DTB、外设固件和数据 schema 的兼容窗口是否机器可判定？
  \item 是否验证了存储接近满载、坏块增加和文件系统异常恢复？
  \item 更新在下载、擦除、写入、校验和切换的每个阶段断电后能否恢复？
  \item 新系统未确认、反复崩溃或看门狗复位时能否自动回退？
  \item 版本、防回滚、产品兼容和签名检查是否在受信任边界内执行？
  \item 差分或流式更新是否验证精确基线、最终摘要和最坏暂存空间？
  \item 分批发布是否具有预定义观察窗口、停止条件和设备端真实状态确认？
  \item 数据迁移失败或系统回退后，配置和业务数据是否仍可解释？
  \item 恢复、返厂和出厂重置是否明确保留/擦除范围并留下审计记录？
\end{itemize}
