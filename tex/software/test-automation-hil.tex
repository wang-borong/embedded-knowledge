\chapter{测试自动化与硬件在环}
\label{chap:test-automation-hil}

嵌入式测试需要同时验证纯软件逻辑、内核接口、完整镜像和真实电气行为。单一测试环境无法覆盖所有故障，因此应建立从主机单元测试到硬件在环的分层体系，并让每一层具有明确的发现目标。

\section{测试金字塔}

推荐层次包括：
\begin{enumerate}
  \item 主机单元测试：算法、解析器、状态机和错误分类；
  \item 仿真与模拟：QEMU、FVP、虚拟外设、fake ioctl 和软件故障注入；
  \item 内核测试：KUnit、kselftest、LTP 和驱动回归；
  \item 板级接口测试：真实 GPIO、总线、DMA、存储和网络；
  \item HIL 系统测试：电源、复位、外部信号、温度和长时间运行；
  \item 生产测试：覆盖装配、器件和身份写入，不重复全部研发测试。
\end{enumerate}

越靠近硬件，测试速度越慢、成本越高且故障定位越困难。应把可脱离硬件的逻辑尽量下沉到快速测试，但不能用 mock 通过替代目标板电气验证。

\section{风险覆盖与测试追踪}

测试集合应从需求、接口、故障假设和历史逃逸缺陷导出，而不是按“每个模块写若干用例”平均分配。高风险电源、存储、执行器、升级和安全边界需要跨层验证；低风险纯显示逻辑通常不值得占用昂贵 HIL 时长。

每个门禁测试至少关联：稳定测试 ID、被验证需求或不变量、目标故障、适用硬件/软件范围、执行环境、判定器版本和原始证据。反向也应能从发布需求查询到覆盖它的测试及最近一次有效结果。测试存在但长期被跳过、只在旧硬件运行或依赖失效仪器时，不应被计为覆盖。

覆盖矩阵需要说明“该层能证明什么”和“不能证明什么”。例如 QEMU 能较早发现启动参数、ABI 和驱动控制流错误，但通常不能证明真实 DDR 时序、模拟电平、缓存一致性细节或掉电波形；HIL 能验证真实电气链路，却不适合穷举协议解析器的全部字节组合。

\subsection{场景契约与判定器}

一个可跨环境复用的测试场景应显式定义：
\begin{description}
  \item[前置状态] 镜像、配置、设备身份、电源状态、存储内容和外部系统状态；
  \item[激励] 输入值、顺序、时间窗口、故障位置、随机种子和终止条件；
  \item[观测] 物理量、总线事务、事件 ID、状态快照和持久化数据；
  \item[oracle] 允许范围、时序、状态不变量、误差与失败分类；
  \item[清理] 恢复输出、释放设备、重建基线以及清理失败时的隔离动作；
  \item[证据] 原始采样、日志、trace、波形、摘要和工具版本。
\end{description}

判定器应优先检查稳定状态和机器可读事件，而不是匹配会随翻译或日志级别改变的文本。对于“不得发生”的行为，需要同时证明观测通道在工作：没有看到错误日志，可能是系统正确，也可能是日志链路已经断开。关键测试可以先注入一个已知自检事件，确认采集路径后再执行正式场景。

超时也必须有语义。业务截止期、设备操作超时、测试步骤超时和整个 job 的基础设施超时应分别记录；只使用一个全局超时会把产品响应慢、模型卡死和实验室网络失联混成同一失败。

\section{SIL、模型在环与虚拟平台}

模型在环（Model-in-the-Loop, MIL）通常让控制算法模型与被控对象或环境模型在同一建模环境中闭环运行，用于在生成或编写产品代码前验证算法。软件在环（Software-in-the-Loop, SIL）则把生成或手写的软件实现编译为主机进程，并由环境模型或测试替身驱动。QEMU 和 FVP 进一步提供目标 ISA、异常、中断与虚拟设备环境\cite{qemu-system-doc,arm-fvp-overview}。这些名词在不同行业的边界略有差异，项目应直接说明被测对象、执行 ISA、时间模型和被替代的硬件，而不是只写缩写。

推荐按以下顺序上移同一组场景：

\begin{enumerate}
  \item 用主机单元测试验证纯计算和状态不变量；
  \item 用虚拟时钟及设备替身验证超时、乱序、重试和资源耗尽；
  \item 在 QEMU/FVP 中验证目标 ABI、启动、异常和完整镜像；
  \item 在目标板上验证真实控制器、DMA、缓存和性能；
  \item 在 HIL 中闭合电气输入、物理对象和故障反应链路。
\end{enumerate}

每上移一层都应复用测试向量、事件 ID 和判定不变量。若每个环境拥有完全独立的脚本与判断逻辑，测试之间无法形成证据链，环境差异也容易被误认为产品差异。

虚拟平台用例应保存模型版本、非默认参数、镜像摘要、DTB/ACPI、随机种子和完整串口。涉及超时时，要区分被测系统的虚拟时间与 CI 主机的墙上时间：前者验证产品语义，后者负责发现模型卡死或基础设施失联。

\section{契约测试与差分测试}

硬件抽象层、驱动与服务之间的接口应具有可在多个环境执行的契约测试。例如一个传感器读取接口不只测试正常值，还应固定验证：短传输、CRC 错误、超时、设备复位、时间戳回退、重复样本和取消请求。

差分测试让同一输入在参考实现、优化实现、模拟器和目标板上运行，再比较稳定语义。适合比较的对象包括：

\begin{itemize}
  \item 协议编码结果、状态转移和错误分类；
  \item 启动阶段、固件 ABI 和设备枚举不变量；
  \item DSP/控制算法在已定义定点误差范围内的输出；
  \item 文件系统或数据库操作后的业务不变量；
  \item 异常原因、恢复动作和安全输出。
\end{itemize}

不应直接比较线程交错、无约束日志顺序、虚拟平台周期数或浮点最后一位。测试 oracle 必须允许规范定义的自由度，同时拒绝会破坏产品契约的差异。

\section{属性测试、模糊测试与变形关系}

协议解析器、文件格式、状态机和数值边界适合由生成器探索大于手写样例的输入空间。属性测试应描述必须始终成立的不变量，例如“编码后再解码保持语义”“无效长度不会越界访问”“重复取消不会重复释放资源”“任何输入都不会产生未声明状态”。

fuzzing harness 应尽量脱离设备，把解析、校验和状态转移编译为主机目标，并结合 AddressSanitizer、UndefinedBehaviorSanitizer 等诊断。发现崩溃后要保存并最小化输入、固定工具链和 sanitizer 配置，再把样本加入回归 corpus。仅保存随机种子但没有生成器版本，通常无法重放历史结果。

当不存在精确参考输出时，可以使用变形关系。例如滤波器输入整体延迟后，稳态输出应保持同样延迟；把无关字段重新排序不应改变规范允许的语义；对同一幂等事务重复发送，最终业务状态应等价。变形关系本身也是需求，必须声明适用范围，不能把本来非线性的系统强行当成线性系统验证。

主机 fuzz 通过不代表目标安全。目标编译器、对齐、字节序、整数宽度、DMA 和中断并发仍需在目标环境复验；反过来，目标板上的一次随机压力也不能替代可重复、可最小化的主机探索。

\section{可测试架构}

驱动访问、时间、随机数、文件系统和网络应通过窄接口注入，使状态机能在主机上控制输入。测试替身必须模拟错误、短读写、超时和乱序，而不只是返回成功。

协议解析器应采用长度受限的纯函数，适合单元测试和 fuzzing。生产状态机应能使用虚拟时钟推进，避免测试依赖真实长延时。

\section{模型保真度与替代边界}

每个模拟器、设备模型和测试替身都应具有能力清单，说明已实现寄存器、副作用、中断、DMA、时钟、复位、错误和性能模型。未实现的访问最好明确失败或记录告警；直接返回零值容易让驱动沿一条现实硬件上不存在的成功路径继续运行。

模型版本升级可能改变设备默认值、指令行为或时间推进方式，应像硬件修订一样进入变更评审。若虚拟平台结果与目标板不一致，应先判断差异属于模型缺失、未定义行为、时序敏感还是产品缺陷，并把结论写入场景资产，避免每次回归都重新争论同一差异。

模型保真度不应以“启动到了 shell”衡量。应按测试目的定义，例如验证启动链需要异常、定时器、串口、存储和设备树足够真实；验证实时响应还需要可信的时间与中断模型；验证模拟前端、电源瞬态和 EMC 则必须转向实物或专用物理模型。

\section{内核测试}

KUnit 适合测试内核内部纯逻辑和边界条件\cite{linux-kunit-doc}；kselftest 验证用户可见内核 ABI\cite{linux-kselftest-doc}；LTP 覆盖广泛系统调用和内核功能。BSP 不需要盲目运行全部测试，但应选择与配置和产品功能相关的集合，并记录跳过原因。

驱动测试应覆盖 probe defer、资源获取失败、IRQ 超时、runtime PM、解绑和模块反复加载。Linux fault-injection 基础设施可以构造内存分配、块 I/O 等失败\cite{linux-fault-injection-doc}；使用 fault injection、kmemleak、KASAN、KCSAN 和 lockdep 时，要区分诊断配置引入的时序变化。

测试报告必须保存内核源码提交、\texttt{.config}、编译器、命令行和实际执行的测试列表。内核自测中的 skip 可能表示功能未启用、硬件不具备、权限不足或 harness 不兼容，不能在汇总时一律当作通过。产品内核裁剪掉某项功能时，应确认对应测试不适用，而不是仅因为测试无法运行就删除记录。

控制协议应返回机器可读状态和时间戳。测试程序不能只等待固定时间再搜索日志，应等待可观测条件并设置总超时。

\section{HIL 控制平面与安全联锁}

HIL 控制器应把 DUT、电源通道、继电器、仪器和线缆拓扑作为版本化资源管理。每个动作返回实际状态，例如电源设定值与测得输出、继电器命令与辅助触点反馈、串口端口与识别到的设备身份。只确认控制 API 返回成功，不能证明物理激励已经到达 DUT。

可能产生危险电压、电流、运动、加热或电池异常的实验必须由独立联锁限制。软件 job 的权限不能覆盖急停、门禁、过流、超温和机械限位；控制主机崩溃、网络断开或脚本超时时，工装应回到规定安全状态。破坏性测试还应使用隔离设备池，避免把受损 DUT 重新分配给普通回归。

测试开始前应执行拓扑自检：核对 DUT 身份、硬件 revision、探头/通道、供电极性、接地、量程和执行器初始状态。若这些前置条件不满足，结果应标为基础设施错误或未执行，而不是让产品用例失败。

\section{时间关联与测量不确定度}

串口、示波器、逻辑分析仪、网络抓包和 DUT trace 常位于不同时钟域。把它们的时间戳直接拼接，会把时钟 offset、漂移和采集缓冲延迟误认为产品延迟。关键场景应使用公共硬件触发、共享参考时钟或可测同步脉冲建立映射，并保存映射残差与不确定度。

端到端时间测试需要明确起点和终点位于哪里。例如“GPIO 输入到电机输出”可以从工装电平跨过阈值的时刻开始，到驱动电压达到规定比例结束；应用日志中的“收到事件”和“已发送命令”只是中间观测点。仪器带宽、采样率、探头负载、触发抖动和软件导出延迟都应计入测量契约。

若测试只需要事件顺序而不需要绝对时间，可以使用单调 sequence 和因果标识减少同步要求。但涉及截止期、同步采样或跨设备控制时，必须给出统一时钟或误差上界，不能用肉眼对齐波形代替量化结果。

\section{测试清单与资产关联}

每次测试必须关联：软件镜像摘要、源码版本、配置、硬件版本、DUT 序列、工装版本、仪器校准状态、环境条件和原始日志。只有测试名称和 Pass/Fail 不能支持复现。

\begin{lstlisting}[language=C,caption={测试结果 manifest 的逻辑字段}]
struct test_run_record {
    char run_id[40];
    char scenario_version[40];
    char image_digest[65];
    char hardware_revision[16];
    char fixture_revision[16];
    char environment_id[32];
    uint64_t random_seed;
    uint64_t started_at;
    uint32_t passed;
    uint32_t failed;
    uint32_t infrastructure_errors;
    uint32_t inconclusive;
    uint8_t evidence_digest[32];
};
\end{lstlisting}

基础设施错误必须与产品失败区分，例如串口采集断开、继电器未动作、仪器超量程和网络存储不可用。否则不稳定工装会污染产品质量数据。

推荐使用至少五类结果：通过、产品失败、基础设施错误、结论不足和未执行。结论不足表示激励发生但关键观测缺失或结果落入预先定义的灰区；未执行则表示前置条件不满足。二者都不能计入通过率，也不应自动归责为产品失败。

重跑必须保留首次结果并建立父子关系。若首次失败、第二次通过，汇总应显示 flaky 或待分类，而不是覆盖为绿色。只有已经证明首次失败来自基础设施瞬态，才可让重跑结果决定产品结论；分类依据、操作者和原始证据仍需保留。

\section{电源循环与掉电注入}

HIL 应能直接切断 DUT 主电源，并测量实际下降曲线。软件 reboot、PMIC orderly shutdown 和拔除外部适配器可能具有完全不同的掉电行为。

随机掉电测试需要记录切断时对应的业务阶段，并在恢复后执行文件系统和业务不变量检查。测试分布应覆盖擦除、写入、fsync、rename、数据库提交和 OTA 切换等关键窗口。

\section{信号与总线故障注入}

可通过模拟开关、可编程负载或协议代理注入断线、短路、抖动、延迟、CRC 错误和设备无响应。注入设备必须保证默认状态安全，并在控制主机崩溃时释放危险输出。

总线分析仪看到的线上事务应与驱动 trace 和应用事务 ID 关联。这样可以区分硬件未响应、驱动未发起和应用超时策略错误。

\section{故障注入矩阵与证据}

同一“超时”可以在多个边界注入：物理设备不响应、控制器丢中断、驱动延迟完成、服务不消费队列或网络代理丢包。测试计划应记录注入层、真实故障假设、预计检测点、最大检测时间、恢复动作、安全输出和复位后状态，避免重复测试同一软件分支却遗漏其他故障域。

每次注入必须包含三段证据：
\begin{enumerate}
  \item 工装或软件确认故障已经实际施加，并记录开始/结束边界；
  \item DUT 在规定时间内检测并给出稳定故障标识；
  \item 系统完成隔离、降级或恢复，且未破坏规定的不变量。
\end{enumerate}

若继电器命令发出但触点没有断开，测试不能宣称产品正确处理了断线；若 DUT 报警但执行器仍保持危险输出，也不能把“检测成功”当作系统通过。故障撤销后的恢复同样需要验证，特别是锁存故障、重连风暴、重复事务和部分初始化资源。

注入强度和持续时间应来自故障模型。过短脉冲可能根本没有跨过硬件滤波，过长短路则可能把可恢复通信故障变成器件损坏。对安全相关输出，应先用限能、替代负载或模拟器验证脚本，再进入真实执行器环境。

\section{长稳与统计}

长稳测试应持续记录内存、句柄、温度、功耗、错误计数、重连次数和最大延迟。只在结束时检查设备是否仍在线，会遗漏逐步退化。

性能结果应保存分布、最大值和测试条件。若系统要求极低失效率，需要根据样本量与运行时间说明统计置信度，不能以少量“零失败”直接证明目标可靠性。

在独立、失效率近似稳定的简化假设下，观察总时长 $T$ 内零失败，对应 95\% 单侧失效率上界约为 $3/T$。该“rule of three”只能用于快速量级检查；温度循环、软件版本变化、相同批次共因和测试中断都会破坏独立同分布假设，正式可靠性结论应使用与任务剖面相符的模型。

长稳中因工装重启、实验室断电或采集丢失而缺少证据的时间不能简单计为成功运行时长。应分别统计 DUT 有效暴露时间、基础设施不可用时间和未观测区间，并保存故障发生前的资源趋势及最后已知进展事件。

\section{覆盖度与退出门}

代码覆盖率可以发现从未执行的分支，但不能说明断言正确、时序窗口充分或硬件故障已覆盖。需求覆盖、接口/状态覆盖、故障注入覆盖、硬件变体覆盖和代码覆盖应分别报告。对于协议和状态机，可以补充 mutation testing 或故意破坏实现，确认现有测试确实能拒绝错误行为。

硬件、温度、供电、软件配置和外设组合很快形成笛卡尔积。应根据等价类、边界值、交互风险和现场分布选择组合，并明确哪些组合只做分析、哪些做抽样、哪些必须全量门禁。高风险新板 revision 不能只因“与旧版相似”继承全部证据。

发布退出门应提前规定必过集合、允许的 skip、已知 flaky 上限、基础设施可用率和残余风险批准人。探索性测试可以发现未知问题，但不能在结果出来后临时把失败用例排除出门禁。测试门的配置本身也应版本化并与发布 manifest 关联。

\section{工装校准与自检}

HIL 本身也是测量系统。电压、电流、时间和温度通道需要校准；继电器和插座有寿命；线缆与探头会改变信号。每次批量测试前应使用参考负载或 loopback 执行工装自检。

工装固件、脚本和接线图必须版本化。修改工装后需要确认历史结果是否仍可比较。

\section{硬件农场生命周期}

共享设备不能只有“空闲/占用”两个状态。推荐至少区分 ready、reserved、recovering、quarantined 和 maintenance，并为每次状态转换记录原因。设备在连续启动失败、身份不匹配、测量自检异常或经历破坏性测试后，应进入隔离，而不是被调度器立即重新上电再分配。

每个槽位需要机器可查询的库存信息：DUT 序列号与硬件 revision、可写镜像类型、调试器、串口、继电器、电源/测量通道、工装 revision、网络拓扑、最近校准和已知限制。调度器按能力选择资源，测试本身再次核对实际身份，防止数据库记录与物理接线漂移。

恢复流程应分级：重新连接采集、受控复位、重新上电、进入恢复模式重刷、工装 loopback 自检，最后才是人工维护。自动恢复次数必须有上限；持续重刷可能掩盖存储退化，也会抹掉最有价值的故障证据。

参考板或 golden unit 用于确认工装趋势，不用于定义产品规格。参考板也会老化、污染或被误刷，应具有锁定镜像、独立保存、周期交叉验证和退役规则。新工装通过参考板只说明它能复现参考结果，还需用已知缺陷样本证明检出能力。

\section{CI 与实验室调度}

硬件资源有限时，CI 应把快速主机测试作为每次提交门禁，把目标板 smoke test 用于合并请求，把长稳、温度和破坏性故障注入安排为周期任务。调度器需要设备锁、超时回收、自动重新上电和隔离故障板。

未经确认不应自动把任意开发分支烧写到共享生产工装。镜像来源、签名和允许的设备池应受到访问控制。

虚拟平台任务还应限制 CPU、内存、磁盘和许可证并发数。模型启动失败、许可证不可用和 worker 资源耗尽属于基础设施错误，不应记为 DUT 功能失败。重复执行只适合确认基础设施瞬态问题，不能用“重跑直到通过”掩盖竞态或时序缺陷。

\section{Flaky 治理与结果保全}

不稳定测试会同时制造两种风险：偶发红灯降低团队信任，偶发绿灯让真实竞态逃逸。每个 flaky 用例应有责任人、首次出现版本、复现概率、受影响环境、隔离期限和退出标准。隔离意味着它暂时不阻塞普通门禁，但仍按计划执行并显著展示结果，不等于删除。

自动重试策略必须按错误类别配置。基础设施连接失败可以在完成资源自检后重试；确定性的断言失败、内核 panic、数据损坏或安全输出错误不应通过重试变绿。重试前若需要重新刷机、清空数据或换板，新的运行已经改变前置状态，必须作为独立样本记录。

CI 应保存失败现场优先于快速回收设备。可采用有界“证据冻结”窗口：保留串口、trace、波形、镜像和设备状态，随后自动导出诊断并将 DUT 隔离；超过保留期限再由明确策略释放。否则最难复现的失败往往在下一 job 上电时被覆盖。

\section{验收清单}

\begin{itemize}
  \item 每种测试层是否具有明确目标，避免重复和空白？
  \item 同一场景能否跨主机、虚拟平台、目标板和 HIL 复用输入与不变量？
  \item 需求、风险、故障假设和测试证据之间是否可双向追踪？
  \item 场景是否明确前置状态、激励、oracle、时间域、清理和证据？
  \item mock 是否覆盖错误、短传输、超时和并发，而不仅是成功路径？
  \item 虚拟时间、墙上时间、随机种子和模型配置是否可追溯？
  \item HIL 能否区分 DUT 失败与基础设施失败？
  \item 每次故障注入是否证明激励实际发生、被检测并完成安全反应？
  \item 测试结果是否关联镜像、硬件、工装、环境和原始日志？
  \item 掉电与信号注入是否达到真实硬件故障边界？
  \item 多仪器时间戳是否具有公共触发、时钟映射或误差上界？
  \item 工装是否具有校准、自检、默认安全状态和寿命管理？
  \item 硬件农场是否能够隔离异常 DUT，并防止无限自动恢复破坏证据？
  \item 长稳结果是否保存趋势、最大值和统计条件？
  \item flaky、skip、重试和结论不足是否受到独立治理而未被计为通过？
\end{itemize}
