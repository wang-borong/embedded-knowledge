RISC-V 由开放且版本化的基础 ISA、标准扩展和特权架构组成，目前由 RISC-V International 维护。开放规范不等于所有实现彼此相同：处理器核、SoC 平台、固件接口、中断控制器、缓存一致性和调试生命周期仍由具体产品决定。

本节以非特权 ISA 与特权架构规范为语义边界\cite{riscvspec,riscvpri}，重点说明软件真正需要固化的工程契约。扩展状态和版本持续演进，目标项目必须保存所用规范、工具链、处理器修订号与平台资料，不能把本节的扩展列表当作当前全部标准的枚举。

\subsection{ISA、ABI 与平台契约}

“支持 RV64”只说明 XLEN 与基础编码的一部分，不能推出乘除法、原子、压缩、浮点、向量、位操作或虚拟化一定存在。一个可复现的软件目标至少包含四层：
\begin{description}
  \item[ISA] 基础指令集、全部单字母与多字母扩展、各扩展版本及 XLEN；
  \item[ABI] 整数宽度、指针宽度、浮点调用约定、栈对齐和目标文件属性；
  \item[特权架构] M/S/U 模式、页表模式、PMP、H 扩展和可用 CSR；
  \item[平台] 启动协议、hart 拓扑、地址图、中断、计时器、SBI、设备发现与缓存一致性。
\end{description}

编译器的 \texttt{-march} 与 \texttt{-mabi}、汇编器属性、链接对象、Bootloader 描述和操作系统运行时探测必须一致。例如，使用 \texttt{lp64d} 编译的对象要求匹配的双精度浮点 ABI，不能只因 CPU 能执行部分 F/D 指令就与软浮点对象任意混合。

\texttt{misa} 不能完整表达所有多字母扩展和平台属性，也不应作为唯一发现机制。裸机固件可以使用生成期 manifest；操作系统通常结合 Device Tree、ACPI、固件接口或架构提供的运行时探测。Device Tree 的 ISA、MMU、hart、中断与 \texttt{timebase-frequency} 属性必须来自真实平台，而不是从 QEMU \texttt{virt} 配置复制\cite{devicetree-spec,qemu-riscv}。

建议把下列信息写入构建与崩溃记录：
\begin{itemize}
  \item 规范版本、ISA 扩展字符串、ABI 和工具链版本；
  \item 处理器核、修订号、SoC 与板级版本；
  \item 缓存 line、大页、ASID、PMP entry 和向量 VLEN 等实现属性；
  \item SBI、Bootloader、Device Tree/ACPI 与操作系统版本；
  \item 已应用勘误、workaround 和验证用例。
\end{itemize}

\subsection{寄存器与调用约定}

RV32I/RV64I 通常提供 32 个整数寄存器，\texttt{x0} 固定为零。标准 ABI 为寄存器赋予稳定角色：
\begin{description}
  \item[控制与平台] \texttt{ra} 保存返回地址，\texttt{sp} 是栈指针，\texttt{gp} 与 \texttt{tp} 分别服务全局与线程局部数据；
  \item[参数与返回值] \texttt{a0--a7} 传递整数/指针参数，\texttt{a0--a1} 也承载常见返回值；
  \item[临时寄存器] \texttt{t0--t6} 由调用者保存；
  \item[保存寄存器] \texttt{s0--s11} 由被调用者保存，\texttt{s0} 也可作为帧指针。
\end{description}

浮点寄存器和参数约定取决于所选 ABI；向量调用约定也不能从“实现 V 扩展”直接推出。中断、信号、内核任务切换和虚拟机切换需要根据状态寄存器判断扩展上下文是否活动，再选择惰性或主动保存策略。

ABI 还定义栈对齐、结构体传递、可变参数、TLS、重定位和代码模型。Bootloader、固件、内核与模块若使用不同代码模型或调用约定，可能在链接阶段不报错，却在远跳转、浮点参数或异常展开时失败。发布前应检查 ELF attributes、反汇编和链接映射，而不是只比较源代码宏。

\subsection{特权级、CSR 与 Trap}

常见特权模式为：
\begin{description}
  \item[M-mode] 机器模式，管理最低层平台状态、PMP 和固件服务；
  \item[S-mode] 监管者模式，通常运行支持虚拟内存的操作系统内核；
  \item[U-mode] 用户模式，运行受限应用；
  \item[HS/VS/VU] H 扩展提供的宿主监管者和客户机监管者/用户执行环境，而不是独立的“H-mode”。
\end{description}

具体实现可以是 M-only 微控制器，也可以提供 M/S/U 与 H 扩展。较高特权级通过 \texttt{medeleg/mideleg} 等机制委托部分 Trap，但委托不是简单的优先级设置；它改变入口 CSR、处理栈、返回指令和安全边界。

常用 M-mode CSR 包括 \texttt{mstatus}、\texttt{mtvec}、\texttt{mepc}、\texttt{mcause}、\texttt{mtval}、\texttt{mie/mip}、\texttt{mscratch} 和 PMP 配置；S-mode 对应 \texttt{sstatus}、\texttt{stvec}、\texttt{sepc}、\texttt{scause}、\texttt{stval}、\texttt{sie/sip}、\texttt{sscratch} 与 \texttt{satp}。CSR 是否存在、哪些位可写以及访问失败如何 Trap，都要按目标规范与实现解释。

Trap 入口不会像 Cortex-M 那样自动压入完整通用寄存器帧。入口汇编至少要：
\begin{enumerate}
  \item 获得不会被当前上下文覆盖的 scratch 或处理栈；
  \item 保存将被修改的寄存器与原始 SP；
  \item 快照 cause、tval、epc、status、特权级和 hart ID；
  \item 区分异常与中断并分发到有界处理路径；
  \item 在返回前恢复前一特权级、中断状态和完整上下文。
\end{enumerate}

\texttt{mtvec/stvec} 可配置 Direct 或 Vectored 模式。Vectored 模式只对中断按 cause 形成偏移，异常仍进入公共基址；入口基址还要满足模式要求的对齐。嵌套 Trap 必须使用 per-hart 栈或帧链，不能让第二次异常覆盖第一份现场。

ECALL、断点、非法指令和页错误具有不同的 EPC 处置。不能统一执行 \texttt{epc += 4}：压缩指令可能为 16 bit，可恢复页错误通常要修复映射后重试原指令，而部分异步错误的 EPC 只表示观察点。崩溃记录应包含镜像 build ID、CSR 快照、Trap frame、页表根、活动中断与平台版本，便于离线符号化。

\subsection{中断控制器与时间基准}

特权架构只规定软件、计时器和外部中断如何进入 hart。具体平台可能使用传统 CLINT/PLIC，也可能采用 AIA 体系中的 ACLINT、APLIC 与 IMSIC。驱动应通过平台描述发现控制器类型、地址和 context，不能把某个开发板或模拟器的固定地址视为 ISA 常量。

PLIC 的典型流程是读取 claim 获得中断 ID，处理设备源，再向 complete 写回同一 ID。设备级清中断、控制器 claim/complete、优先级阈值和 context enable 的顺序共同决定是否丢中断或重复触发。IMSIC 以面向 hart 的消息表示中断，更适合 MSI、PCIe 和虚拟化，但仍要定义消息 ID 分配与客户机注入边界。

\texttt{time} 计数与 CPU 主频不是同一概念。平台必须给出稳定的 timebase 频率、跨 hart 同步保证、低功耗行为和回绕语义。S-mode 通常通过 SBI 设置定时事件；所用 SBI 扩展、返回码、并发与阻塞属性必须与固件版本匹配\cite{riscv-sbi}。

中断验收应测量从设备事件到首条处理指令、设备确认完成和业务任务被唤醒的端到端延迟，并覆盖屏蔽窗口、嵌套、缓存冷启动、共享互连和目标最低频点。只测空闲系统中的 Trap 入口周期数不能证明实时边界。

\subsection{启动、hart 生命周期与固件边界}

复位后的 PC、可用 hart、内存状态和设备默认值属于平台契约。每个 hart 都需要独立栈、Trap scratch、per-CPU 数据和页表切换状态；主 hart 负责全局初始化并不意味着次级 hart 可以在共享状态发布前提前访问。

多 hart 启动应使用 acquire/release 原子或平台规定的屏障发布阶段状态。启动 epoch 需要拒绝旧消息和上一次运行留下的完成标志；仅把共享变量声明为 \texttt{volatile} 不能提供跨 hart 顺序。

SBI 为 S-mode 软件提供计时器、IPI、远程 fence、hart state management、系统复位等标准服务，但扩展集合与版本需要运行时探测。调用方应处理不支持、拒绝、已启动和暂时失败等结果，不能假设所有 OpenSBI 或厂商固件行为一致。

Linux 启动还规定进入模式、寄存器参数、页表与中断状态等约束，应使用目标内核文档而非过时样例\cite{linux-riscv-booting}。Bootloader 传递的 Device Tree 必须描述实际内存、保留区、hart、ISA、PLIC/AIA、计时器和设备；镜像、DTB、固件与远端核版本应作为整组兼容单元更新。

\subsection{PMP、DMA 与物理隔离}

PMP 由 M-mode 配置物理地址匹配和 R/W/X 权限，用于限制较低特权模式。常见匹配形式包括 TOR、NA4 和 NAPOT；entry 数量、最小粒度、优先级、锁定位和可选增强扩展均由实现决定。

TOR 区域的下界来自前一个 entry，因而排序本身就是安全语义。锁定 entry 后通常要到复位才能修改，并可能影响 M-mode 访问。设计默认拒绝策略时，需要为固件调用缓冲、共享页、只读测量区和设备 MMIO 建立最小窗口，同时验证区域边界和空洞。

PMP 只约束 hart 发起的访问，不自动限制 DMA、调试模块、NPU 或其他总线主设备。完整隔离还需要 IOMMU/IOPMP、SoC 防火墙、设备复位、缓存所有权与调试认证。安全启动只证明初始镜像，若后续 M-mode 固件可以任意改写 PMP 或开放调试，运行时边界仍然不成立。

PMP 验收应包含越界读写取指、重叠 entry、锁定后修改、Trap 入口栈、固件调用缓冲和 DMA 绕过测试。H 扩展、PMP 与设备直通的组合边界见第~\ref{chap:virtualization-isolation}~章。

\subsection{虚拟内存与 TLB 一致性}

常用页表模式如下，均以 4 KiB 为基础页并支持满足对齐要求的更大页：
\begin{table}[H]
  \centering
  \caption{常用 RISC-V 地址转换模式}
  \begin{tabular}{llll}
    \hline
    模式 & XLEN & 页表级数 & 规范虚拟地址宽度 \\
    \hline
    Sv32 & 32 & 2 & 32 bit \\
    Sv39 & 64 & 3 & 39 bit \\
    Sv48 & 64 & 4 & 48 bit \\
    Sv57 & 64 & 5 & 57 bit \\
    \hline
  \end{tabular}
\end{table}

\texttt{satp} 选择地址转换模式、ASID 和根页表。写入页表后，软件必须按作用域使用 \texttt{SFENCE.VMA} 协调当前 hart 的地址转换缓存。若映射可能被其他 hart 使用，还需要发布页表写入、发送 shootdown、让目标 hart 执行 fence、等待确认，再回收旧页或物理内存。

PTE 的 V/R/W/X/U/G/A/D、PPN 与保留位必须按目标规范组合。非法 R/W 组合、未对齐大页、A/D 位更新策略和权限提升都需要测试。页表 walker 是否与数据缓存一致、是否可能读取旧 PTE，以及 IOMMU 是否使用另一套页表，属于具体 SoC 契约。

TLB shootdown 是分布式协议，不是单条指令。超时、离线 hart、低功耗唤醒和重复 IPI 都要定义；在所有观察者确认前回收旧页，会形成低概率但严重的数据破坏。

\subsection{RVWMO、原子与代码更新}

RISC-V 默认内存模型 RVWMO 允许不同 hart 以弱顺序观察普通内存访问。同步应优先使用 C/C++/Rust 原子、锁和操作系统 API，让工具链依据目标扩展生成 acquire/release、AMO、LR/SC 或 fence。手写汇编必须同时维护编译器与硬件顺序，不能只插入一条 \texttt{FENCE} 后假定正确。

A 扩展提供原子内存操作以及 load-reserved/store-conditional。reservation 的粒度和失效原因是实现属性，SC 可以因中断、另一 hart、缓存替换或实现行为失败；无界重试不能直接进入硬实时路径。LR/SC 对设备 MMIO 通常也不是可移植同步方式。

\texttt{FENCE} 的 predecessor/successor 集合区分设备输入、设备输出、内存读和内存写。语言原子不能把 MMIO 变成普通缓存一致 RAM；设备寄存器、posted write 和 DMA 所有权应使用平台 accessor 与 DMA API。跨核与设备边界的完整方法见第~\ref{chap:realtime-language-memory-model}~章。

\texttt{FENCE.I} 只保证当前 hart 后续取指观察到先前指令存储更新。JIT、模块加载或补丁跨 hart 发布时，还要通知其他 hart 执行取指同步；S-mode 可以使用 SBI remote fence 或操作系统 IPI 协议。写代码页、清数据缓存、修改权限和刷新取指的顺序必须由目标平台共同定义。

\subsection{扩展、上下文与可移植性}

常见扩展对软件契约的影响包括：
\begin{description}
  \item[M] 提供乘除法，但具体延迟、是否早退和实时上界属于微体系结构；
  \item[A] 提供原子操作，并要求缓存、一致性或 reservation 机制与软件同步匹配；
  \item[C] 提供 16 bit 压缩编码，影响代码密度、反汇编、EPC 推进与补丁边界；
  \item[F/D] 提供单/双精度浮点状态，影响 ABI、异常、信号和任务上下文；
  \item[B 与密码扩展] 提供位操作或算法加速，但具体子扩展需单独探测；
  \item[V] 提供向量长度无关执行模型，程序不能假定固定 128 或 256 bit 宽度；
  \item[Zicsr/Zifencei 等] 多字母扩展独立版本化，不能从基础字母组合隐含推出。
\end{description}

V 扩展通过 \texttt{vsetvl/vsetvli} 根据剩余元素、SEW、LMUL 和实现 VLEN 选择本轮 VL。可移植算法应 strip-mine 数据并覆盖不同 VLEN。操作系统还必须保存 \texttt{vl}、\texttt{vtype}、\texttt{vstart}、向量寄存器及相关控制状态；惰性保存需要与异常、信号、迁移和虚拟机切换共同验证。

浮点与向量上下文会显著增加 Trap 和任务切换成本。工具链可能在普通 C 代码中自动向量化或使用浮点寄存器，因此“源代码没有显式 intrinsic”不能证明扩展状态未被使用。应检查反汇编，并通过构建 profile 限制硬实时路径可用扩展。

\subsection{调试、PMU 与性能证据}

RISC-V Debug Specification 定义 Debug Module、hart halt/resume、abstract command、\mbox{program buffer} 和 trigger 等机制；SoC 还需要 DTM、复位连接和认证策略。调试器暂停单个 hart 时，其他 hart、DMA 与外设可能继续运行，现场一致性不能由“全部寄存器已读出”自动保证。

量产生命周期应分别定义开发、制造、返修和现场状态下的调试权限、认证、失败锁定和审计。PMP 不是调试访问控制；若 Debug Module 能绕过系统总线权限，安全边界必须在芯片级关闭或认证。

性能证据可以来自 \texttt{cycle}、\texttt{time}、\texttt{instret} 和实现定义的 HPM counter。事件编码、特权过滤、溢出、多路复用和计数权限均可能不同。比较两个实现时必须固定工作负载、编译器、频率、缓存状态、DDR 与热条件，并同时记录指令数、周期、未命中、带宽和分位延迟。

模拟器适合验证 ISA 功能、Trap、页表和启动协议，但不能证明真实分支预测、缓存替换、互连、DDR、PMU 事件和功耗时序。性能与容量验收方法见第~\ref{chap:performance-capacity-engineering}~章。

\subsection{实现验证闭环}

一个可复现的 RISC-V 平台验证至少包括：
\begin{enumerate}
  \item 生成 ISA/ABI/特权/平台 manifest，并核对 ELF attributes 与运行时发现；
  \item 验证冷启动、次级 hart 启停、复位原因、DTB 与 SBI 扩展；
  \item 对每类 Trap 检查帧布局、压缩指令、嵌套和不可恢复路径；
  \item 运行原子与内存序 litmus，覆盖多 hart、DMA 和代码更新；
  \item 压测页表更新、ASID、TLB shootdown、大页与 hart 离线；
  \item 验证 PLIC/AIA、timer、IPI、优先级、屏蔽和中断风暴恢复；
  \item 对 PMP、DMA、调试和固件调用执行越权与故障注入；
  \item 在目标板记录 PMU、trace、功耗、热稳态和最坏延迟。
\end{enumerate}

第~\ref{chap:case-rustos}~章给出基于 QEMU \texttt{virt}、OpenSBI 和 Rust 的操作系统实践路径，覆盖 FDT、Sv39、Trap、PLIC、调度、进程、VirtIO 和文件系统。该案例适合验证接口与软件结构，真实产品仍需重新验证目标 SoC 的缓存、一致性、PMP、中断与电源行为。

\subsection{RISC-V 系统检查清单}

\begin{itemize}
  \item ISA 扩展及版本、ABI、ELF attributes、工具链与运行时发现是否一致？
  \item Trap 入口是否覆盖压缩指令、嵌套、per-hart 栈、页错误和异步故障？
  \item PLIC/AIA、timer、IPI 和 SBI 是否来自平台描述而非固定地址？
  \item 启动与 hart 状态机是否具有 epoch、超时、幂等和失败恢复？
  \item PMP、DMA/IOPMP、调试、M-mode 固件和安全启动是否形成完整边界？
  \item 页表发布、TLB shootdown、代码更新和旧页回收是否有确认协议？
  \item RVWMO、LR/SC、AMO、FENCE 与 MMIO/DMA 是否分别用于正确观察者？
  \item 浮点与向量上下文是否与 ABI、任务切换、信号和虚拟化一致？
  \item PMU 事件、模拟器结果与目标板数据的适用边界是否写入报告？
  \item 崩溃记录能否关联 hart、CSR、页表、镜像、DTB、SBI 和硬件修订号？
\end{itemize}
